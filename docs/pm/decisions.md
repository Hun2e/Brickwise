# 설계 결정 기록 (ADR)

> 설계문서의 "선택한 이유 · 겪은 문제 · 해결 과정"에 그대로 옮겨 쓸 재료.
> 형식: 번호 · 날짜 · 결정 · 배경 · 대안 · 결과/후속

## ADR-001 · 2026-10-21 · 프론트엔드는 Vanilla HTML/CSS/JS + FastAPI, Streamlit 병행
- 배경: 심화 F2013은 "HTML, CSS, JavaScript로 화면 구현, 화면과 서버 분리, 요청·응답 형식 정의"를 요구한다.
- 결정: 빌드 도구 없는 Vanilla JS로 `web/`을 만들고 FastAPI(`server/`)가 REST API와 정적 파일을 제공한다. 필수 UI인 Streamlit(`app_streamlit.py`)도 유지하고, 두 UI가 같은 `src/rag_service` 서비스 함수를 공유한다.
- 대안: Vite+TS, React — 명세 문구와 거리가 있고 제출물에 빌드 절차가 추가되어 제외했다.
- 결과: 제출 시 "필수 구현과의 결과 비교"를 같은 백엔드 기준으로 할 수 있다.

## ADR-003 · 2026-10-21 · 도메인: 보드게임 RuleJudge
- 배경: 사용자가 국가유산·의약품 후보 대신 보드게임 규칙 판정 서비스를 직접 제안했다.
- 결정: 항목(RAG 1) = 보드게임(기본판·확장판) 100건 이상, 외부 문서(RAG 2) = 공식 규칙집·확장판·FAQ·정오표(MVP 게임) + 위키백과. 핵심 특화 기능(F2010) = 규칙 판정 카드.
- 근거: `docs/planning/01_데이터출처조사.md` — 카탄·루트·윙스팬의 공식 문서에 접근 가능함을 확인했다. BGG API는 토큰 없이 401을 반환한다.
- 미결: MVP 게임, 언어 전략, 저작권 운영, BGG 사용 여부, PDF PoC, 그래프 구조 (기획서 §10 D1~D6).

## ADR-004 · 2026-10-21 · 도메인 변경: 보드게임 → LEGO (Series Archive AI + Custom Build Planner)
- 배경: 사용자가 도메인을 레고로 바꾸고 두 서비스(시리즈 지식 RAG + 보유 세트 기반 조립 분석)를 결합한 기획을 지시했다. ADR-003(보드게임)은 대체되었고, 문서는 `docs/planning/archive_boardgame/`에 보관한다.
- 조사로 확정된 제약 [확인]:
  - LEGO.com 약관이 AI 운영 목적 이용을 금지한다 → LEGO 공식 콘텐츠·설명서는 링크만 제공한다.

  - Brickipedia API는 정상이고 CC-BY-SA다. 스타워즈 표본 20/20 세트에 문서가 있다.
- 실측 발견: 스타워즈 세트 3개를 보유했다고 가정하면, 색상 일치 기준으로 100% 조립 가능한 공식 세트는 0개다. → B의 핵심 UX는 "부족 부품 최소 순위"로 정한다.
- 미결: L1~L7 (1차 검토안 §14).

## ADR-006 · 2026-10-21 · 아키텍처: 오케스트레이터 + 필수 2노드 RAG 그래프 + 결정적 planner
- 결정:
  - 질의 라우팅(fact·filter·set_ops·narrative·compare·build·build_archive)은 `services/orchestrator.py`가 맡는다.
  - 과제 필수 RAG 그래프는 retrieve→generate 2노드를 유지한다. DB·planner 결과는 state의 `injected_cards`(근거 카드)로 주입한다.
  - 답변의 숫자·세트 번호는 사후 검증해서, 근거 카드에 없으면 문장을 제거한다.
  - 검색 기본값은 Hybrid(BM25+Vector, RRF) 후보이고 실험(X1)으로 확정한다. Rerank는 실험군으로 둔다.
- 대안: 그래프 안에 router·db·planner 노드를 두는 방식은 F2007 "두 노드 구성" 검증과 충돌할 수 있어 제외했다. Graph RAG는 관계를 SQL로 충분히 처리하므로 제외했다.
- 산출물: docs/planning/03_아키텍처설계서.md, 04_개발로드맵_WBS.md

## ADR-007 · 2026-10-21 · 구조화 출력 방식: json_mode + Pydantic 검증
- 근거: T-004 스파이크(GMS gpt-5.4-nano, 150회). 세 방식 모두 파싱 100%였지만, Router 정확도는 json_mode 25/25, json_schema·function_calling 22/25였다(build를 build_archive로 오분류). 입력 토큰도 json_mode가 20~30% 적었다.
- 결정: `structured_method=json_mode`, Pydantic 검증 + 재시도 1회 + 원문 JSON 복구. `send_temperature=true`(0) — GMS가 허용함을 확인했다.
- 한계·후속: 표본이 작으므로 E-ROUTE(60문항)로 다시 검증한다. build/build_archive는 규칙 기반 1차 분류를 둔다. P1의 `purpose` 필드를 축소해 지연(약 2초)을 줄인다.

## ADR-008 · 2026-10-21 · RAG 코어 설계 결정 (사용자와 함께 결정)
- 진행 방식: PM이 선택지·근거·권장안을 제시하고 사용자가 2라운드에 걸쳐 직접 결정했다.
- 1라운드 (데이터·색인)
  1. **문서 연결**: 기체 단위 위키 문서는 1벌만 청킹·저장한다. 청크 메타 `sets` 배열에 연결 세트를 두고 Chroma `$contains`로 필터링한다 (Chroma 1.5.9 지원 확인).
     - 주의: 새 세트를 연결할 때 `sets`를 합집합으로 갱신한다 (F2005의 덮어쓰기 경고 대응, 테스트로 고정).
  2. **기체 매핑**: 세트명 키워드 규칙과 검수된 별칭 사전으로 결정적으로 매핑한다. 매핑되지 않은 세트는 시리즈 문서만 근거로 쓴다.
  3. **수집 시점**: 하이브리드. 시리즈·매핑 기체 문서는 사전 수집하고, 질문 시점에는 P1·P2로 부족분만 보충한다 (F2003·F2004 시연 유지).
  4. **항목 텍스트(set_meta)**: 기본 필드(세트명·번호·연도·테마·부품 수)에 **미니피그 이름 + 한국어 별칭**을 넣는다. "같은 기체 다른 판본"은 넣지 않는다 → 판본 비교는 compare 경로(SQL)가 전담한다.
- 2라운드 (검색·생성)
  5. **검색**: 유사도 기준선으로 구현한다. MMR·BM25·Hybrid·Rerank는 인터페이스만 열어 두고 M6 실험에서 추가해 기준선 대비 개선폭을 보고한다.
  6. **청킹**: 섹션 우선 + 상한 1,000자/중복 200자, 청크 앞에 `[문서 › 섹션]` 머리말을 붙인다. 40자 미만 섹션은 인접 섹션과 병합한다 (실측 섹션 길이 89~5,776자).
  7. **근거 수**: 외부 문서 Top-k 5. 선택 세트 메타 1건과 DB 근거는 별도로 항상 포함한다. X3 실험에서 3/5/8을 비교한다.
  8. **답변**: 한국어 서술, 고유명사 영문 병기, 주장마다 `[근거 N]`, 세트별 대화의 최근 4턴을 맥락으로 쓴다.
- 반영: AGENTS.md 청크 ID 규칙, 데이터 수집 설계서 §3.2, 아키텍처 설계서 §4.2를 수정했다.

## ADR-009 · 2026-10-21 · ADR-008 결정 6 보정: 짧은 섹션 병합 기준 40자 → 200자
- 근거: T-006 실측. 수집된 11문서를 1,000/200, 40자 미만 병합으로 청킹하면 269청크 중 200자 미만이 26개(9.7%)였다. 짧은 청크는 임베딩 의미가 약하다.
- 결정 (사용자): 200자 미만 섹션은 같은 상위 섹션 안의 인접 섹션과 병합한다. 상한 1,000자는 유지한다.
- 함께 결정
  - 한국어 링크 문서도 색인한다 (영어 문서의 `sets` 상속).
  - 일반 집단 문서(group)는 색인하되 `entity_kind` 태그를 달아 T-008·M6에서 조정한다.
  - `sets` 배열은 증분으로 덧붙이지 않고 색인할 때마다 `set_entities` 전체에서 다시 계산한다 (덮어쓰기 문제를 구조적으로 제거).

## ADR-010 · 2026-10-21 · 질문 시점 수집 설계 (사용자 검토)
- 문제: T-006 색인은 연결 세트를 `set_entities`만으로 계산하고 대상 밖 문서를 삭제한다 → 질문 시점에 수집한 문서가 다음 색인에서 사라진다.
- 결정
  1. `collect.sqlite.question_links`에 (세트, 문서, 검색어, 선택 이유)를 저장한다. 연결 세트와 색인 대상은 "매핑 ∪ 질문 연결"로 **전체 재계산**한다 (ADR-009 원칙 유지).
  2. P1 v2: 위키 검색용 짧은 키워드(세트 번호·LEGO·따옴표 금지, 최대 3개, purpose 40자). 실측상 v1 검색어는 0건이거나 시리즈 문서에 쏠렸다. v1은 비교용으로 남긴다.
  3. 목록 문서는 사전 매핑에서는 제외(T-005)하고, 질문 시점에는 P2 선택을 허용한다 (`entity_kind=list`).
  4. 질문당 최대 2문서, 시간 예산 30초. 넘으면 확보한 근거로 진행한다 (`partial`).

## ADR-011 · 2026-10-21 · RAG 그래프 검색·생성 결정 (사용자 검토)
- 근거: T-008 실측.
  - 원 질문만 쓰면 한국어 시리즈 문서가 상위를 차지했고, 영어 확장 질의를 쓰면 기체 문서 위주가 되었다.
  - 목록 문서 하나가 top-10을 독점했다.
  - AAT 질문에서 P3가 근거 밖 추론을 했다.
- 결정
  1. 검색 질의 = 원 질문 + P1 `en_terms`. 메타 카드는 ID로 항상 포함한다.
  2. 다양성은 결정적 상한으로 막는다: 후보 20개에서 문서당 ≤2, 시리즈 ≤2, group ≤2, list ≤2로 top-5를 고른다. MMR(F2014)은 M6에서 이 규칙과 비교한다.
  3. 질문 시점 수집은 retrieve 노드 안에서 호출한다 (2노드 유지).
  4. P3는 강화 지시를 쓴다: 근거가 직접 답하지 않으면 "확인되지 않음", 확인된 것과 확인되지 않은 것을 구분, 시리즈 세트 목록은 목록 질문일 때만 근거로 쓴다.
  5. 답변 근거 번호는 원래 번호를 유지한다 (본문과 화면 번호 일치, 과제 4.3).

## ADR-012 · 2026-10-21 · M4 통합 질의 설계 (사용자와 공동 결정, 2라운드)
- 1라운드 (질의 처리 골격)
  1. **라우팅**: LLM 우선(json_mode 라우터, T-004에서 25/25) + 규칙 안전장치. 라우터 응답은 캐시한다.
     - 컬렉션이 없는데 build 계열이면 등록 안내로 바꾼다.
     - build_archive인데 서술 표현이 없으면 build로 바꾼다.
     - (ADR-006의 "규칙 우선"을 실측 근거로 뒤집음)
  2. **DB 경로 답변**: 혼합 (사용자 선택, PM 권장안과 다름).
     - **fact·set_ops·build는 템플릿 문장 + 표** (LLM 미사용, 환각 0, 빠름)
     - filter는 세트 카드 목록 + 적용 필터 표시
     - narrative·compare·build_archive만 P3를 쓴다.
     - 템플릿 답변도 근거 카드 번호(`[근거 N]`)를 단다 (F2008 형식 통일).
  3. **수치 사후 검증**: 근거 카드에 없는 숫자·세트 번호가 든 문장은 제거하고 경고를 표시한다. DB에 없는 세트 번호도 제거한다.
  4. **결합 질의 선택 기준**: Filter 프롬프트가 `{sort, order, max_missing, ...}`를 추출하고, 코드가 planner 결과에서 선택한다 (결정적·검증 가능).
- 2라운드 (기능 세부)
  5. **조건 탐색(F2011)**: SQL 필터(연도·부품 수·미니피그 등 수치 조건) → set_meta 유사도 정렬(의미 조건) → LLM 검수(의미 조건 위반 후보 제거) → 세트 카드. 명세 예시 "LLM이 조건에 맞는 항목만 선별"을 수치 정확성과 함께 충족한다.
  6. **판본 비교 대상**: 기체 매핑(`set_entities`)으로 찾고, 이름에 변형 표지(Microfighter·Cockpit·Diorama·Mini·Midi·Bag Charm 등, 설정값)가 있는 세트는 비교 표에서 빼고 "기타 변형 N개"로 표기한다.
  7. **p3-v2**: "이 기체/이 세트"는 선택 세트가 묘사하는 대상으로 해석하고, 레고 제품 자체 정보는 근거에 있을 때만 답한다. T-008 대표 10문항으로 v1과 나란히 비교해 나아지면 기본값으로 바꾼다.
  8. **오케스트레이터 구조**: ADR-006대로 그래프 밖 Python 오케스트레이터(`services/orchestrator.py`)가 라우팅을 맡는다. 필수 RAG 그래프는 2노드를 유지하고 DB 카드는 `injected_cards`로 주입한다.
- 작업 분할 (M4)
  - T-009: DB 질의(`db/queries.py`: fact·filter·set_ops·compare, 변형 제외) + DB 근거 카드 + 템플릿 답변 (LLM 없음)
  - T-010: 조건 탐색 F2011 (Filter 프롬프트 → SQL → 의미 정렬 → LLM 검수 → 카드)
  - T-011: 라우터 연결 + 오케스트레이터 (7개 경로, compare·build_archive는 RAG 그래프에 카드 주입, 결합 질의 선택)
  - T-012: 수치 사후 검증 + p3-v2 (PM이 v1·v2 비교)
  - 의존 관계: T-009 → T-010·T-011 → T-012. T-010은 T-009 이후 T-011과 파일이 겹치지 않는다.

## ADR-013 · 2026-10-22 · 조건 탐색: 완화 없음 + 추출 조건의 결정적 검증
- 근거: T-010 프로토타입. LLM이 의미 조건("우주선")을 세트명 필수 단어(`Star`, `ship`)로도 넣어 SQL이 0건이 되었다. 의미 정렬은 거리 1.56~1.67로 구분력이 약해 피규어·비행체가 섞였다.
- 결정 (사용자 검토)
  1. 0건이면 조건을 완화하지 않고 "조건에 맞는 세트가 없습니다"로 안내한다 (PM 권장안 "이름 조건만 완화"와 다른 선택).
  2. 대신 LLM이 만든 조건을 막는다: `name_keywords`·`exclude_keywords`·`minifig`는 질문 원문 또는 별칭 사전으로 확인되는 단어만, 수치 조건은 질문에 숫자가 있을 때만 받아들인다. 나머지는 코드가 버린다.
  3. 의미 조건은 SQL 후보 안에서 set_meta 유사도로 정렬한 뒤 LLM이 위반 후보만 뺀다. 수치 판단은 하지 않는다.
  4. 제외된 후보는 개수와 펼치기로 보여 준다. 기본 정렬은 의미 관련도순이다.
- 교훈: json_mode는 스키마를 모델에 전달하지 않는다. 프롬프트에 JSON 키와 예시를 명시해야 한다.

## ADR-014 · 2026-10-22 · 수치 사후 검증 규칙과 P3 v2 채택
- 검증 규칙 (사용자 검토)
  - 허용 집합 = 답변이 인용한 카드의 숫자 + 질문 원문의 숫자 + 오케스트레이터가 해석한 세트 번호
  - 정규화: 콤마·소수·퍼센트, 세트 접미사, 영어 숫자 단어
  - 단위 없는 한 자리 수는 검사하지 않는다.
  - 위반 문장은 제거하고 경고한다. DB에 없는 세트 번호는 무조건 위반이다.
- 실측: 기존 답변 13건 오탐 0 (정규화·맥락 반영 후), 의도적 위반 5/5 제거
- P3 v2: 13문항 비교(문장 −20%, 인용 +5, 지연 −0.4초, 검증 제거 0) → **사용자 결정으로 기본값 채택**
- 남은 문제 → M6: 판본 비교의 표 행 반복(프롬프트보다 요약 카드 주입으로 구조적 해결), 글자 띄어쓰기 이상 재현 확인
- 교훈: 설정 기본값을 읽어 검사하는 테스트는 설정 변경에 깨진다 → 테스트는 검사 대상 버전을 명시한다.

## ADR-015 · 2026-10-22 · M5 화면 설계 (사용자와 공동 결정, 2라운드)

  6. **사용자 구분**: 익명 UUID. 웹은 localStorage, Streamlit은 URL 쿼리 파라미터 `uid`. `conversations`·`collections`의 키로 쓴다.

  8. **작업 분할 (순차)**
     - T-013: 공통 서비스(대화 저장·익명 사용자·상태 점검·세트 목록 검색) + Streamlit (F2009·F2011·F2012)
     - T-014: FastAPI 계약 + SSE (F2013)

## ADR-017 · 2026-10-22 · 검색 기본값 교체: MMR + 질문 원문 질의 (F2014, 사용자 결정)
- 근거 (T-017, 스냅샷 m6-base, 검색 40문항): 기준선(similarity·후보 20·문서당 ≤2·질문+영어 확장)의 섹션 R@5는 0.650(26/40)이었다. 새 설정은 **0.875(35/40, +9문항)**다.
  - 한국어 문서 0.538 → 0.923, 영어 문서 0.857 → 0.786(−1문항, RV-35 "레아도 제다이 훈련을 받았어?": 한국어 질문 → 영어 정답 문서)
  - MRR 0.558 → 0.743, 문서 R@5 0.75 → 0.95. 5개를 다 채우지 못하던 문항 29 → 0
- 원인 분석
  1. 질의 뒤에 붙는 P1 영어 확장어가 검색을 영어 문서 쪽으로 끌어당겨 한국어 문서가 후보 20개에도 들지 못했다.
  2. 후보 20개가 한 문서에 몰리면 "문서당 ≤2" 상한 뒤에 빈자리가 남았다(14문항이 2개만 받음).
- 새 기본값
  - `search_type: mmr`, `mmr_fetch_k: 40`, `mmr_lambda: 0.7`, `mmr_apply_caps: false`, `query_mode: question`
  - P1은 계속 질문 시점 수집(위키 검색어)에 쓴다. 다만 저장소 검색 질의에는 붙이지 않는다.
- **ADR-016 ④⑥ 해석·예외 (사용자 결정)**
  - 지연 기준 "증가 20% 이내"는 **종단 응답 시간** 기준으로 해석한다. 검색 함수 단독 지연은 3.9 → 8.5ms(+4.6ms)로, 종단 5~46초의 0.1% 미만이다.
  - "언어별 회귀 금지"를 영어 문서 1문항만큼 **의도적으로 완화**했다. +9문항 개선과 한국어 사용자 다수라는 점을 감안했다.
  - 대안 MMR + 확장 유지(30/40)는 모든 규칙을 통과했지만 개선 폭이 작다. dual(35/40)은 MRR이 더 낮고 질의 임베딩이 2회다.
- 위험과 후속
  - 약 26개 설정을 같은 40문항으로 골랐으므로 과적합 위험이 있다. 다만 개선 폭(+22.5%p)이 1문항 단위 잡음보다 훨씬 크다.
  - T-018·T-019 이후 평가셋으로 회귀를 다시 확인한다.
  - 한국어 질문 → 영어 정답 문서 유형은 dual 질의나 언어별 질의로 보완하는 것을 로드맵 후속으로 둔다.
- 운영 확인 (질문 시점 수집 포함 실제 답변)
  - 75312-1 "보바 펫은 어떤 캐릭터야?": 한국어 보바 펫 문서 근거로 정답. 기존에는 영어 청크 2개만 받았다.
  - 75423-1 레드 파이브: 정답.
  - 75352-1 팰퍼틴: 정답.

## ADR-018 · 2026-10-22 · 대화 중심 챗봇 UX (ADR-015 일부 대체)
- 배경: 기능(M1~M6)은 완성됐다. 하지만 탭 3개와 thread(탭·세트 번호) 키 때문에 검색 → 질문 → 보유 등록 → 추천이 한 대화로 이어지지 않는다(실측: 이전 결과·조건 미보존, 서수 해석 없음, 채팅 등록 불가, 되묻기 미연결).
- 결정 (사용자 확정: 한 대화 중심 UX. 나머지는 PM 권장안 — 상세는 `docs/planning/05_대화UX설계.md`)
  1. **화면**: 탭을 없애고 단일 대화창으로 바꾼다. 상단에 현재 대상 바([변경]·[해제])를 두고, 결과는 대화 안 카드로 보인다. 보조 패널에는 대화 목록·내 컬렉션·세트별 기록을 둔다. 근거 패널과 `[근거 N]`은 유지한다. → ADR-015 ①②⑥(탭·세트 선택 상자·thread 키)을 대체한다.
  2. **대화 상태**: 대화마다 구조화 상태(subject·last_list(표시 순서·spec·추천 파라미터)·compare·mode·pending)를 저장하고 낙관적 버전을 둔다. "첫 번째"는 실제 표시한 목록 순서를 기준으로 한다.
  3. **해석 우선순위**(결정적, 라우터 이전): pending 응답 > 명시 대상 > 서수 > "그중" 정제 > 지시어 > 모드 후속. 모호하면 되묻는다(추측 금지). 초기화 규칙은 05 문서 §3.3 표를 따른다.
  4. **라우터**: router-v4는 구조화 문맥 요약을 받는다(캐시 키 분리). T-019 `_rules`와 ADR-017 검색 기본값은 유지한다.
  5. **대화 기반 컬렉션 변경**: 6가지 표현 의미를 고정한다(설정·증가·수정·제거·변경 없음·보유 진술). 결정적 의도 사전, DB 존재·수량 검증, 한 트랜잭션 처리, `request_id` 멱등, 커밋 후 성공 알림, 변경과 설명 단계 분리.
  6. **F2009**: 통합 타임라인·세트별 기록(`turn_subjects` primary/compared)·모델 문맥(같은 대상 턴만)을 분리한다. 검증 기준 (a)~(f)를 둔다. 세트 태그만으로는 충족으로 보지 않는다.
  7. **마이그레이션**: 비파괴(추가만, 백업, 멱등). 기존 thread마다 레거시 대화 1개. 구 `/api/threads*`는 제출까지 읽기 전용으로 둔다.
  8. **템플릿 문장**: LLM 없이 문장만 개선한다. "만들 수 있다"는 부족 0일 때만 쓴다.
  9. **작업**: T-021 저장·상태 → T-022 컬렉션 변경 ∥ T-023 해석·정제·라우터 → T-024 채팅·API → T-025 화면 → T-026 종단·회귀. 그 뒤 M7.
- 미결(권장안을 기본값으로 진행하고, 사용자가 바꿀 수 있다)
  - ① 보유 진술이 기존보다 적으면 줄이기 전에 확인한다.
  - ② 레거시는 thread별 대화로 옮긴다.
  - ③ 여러 대화를 제공한다.
  - ④ 구 API는 제출까지 읽기 전용으로 둔다.
