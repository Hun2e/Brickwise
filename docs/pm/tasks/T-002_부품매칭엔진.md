# T-002 Build Planner 부품 매칭 엔진 (집계·부족 분석·추천·컬렉션)

- 상태: 완료
- 관련 요구사항: PRD B-01, B-02, B-03, B-04, B-05(exact·ignore_color), B-06, B-08 / 과제 F2010(도메인 특화 기능의 계산 기반), NF2001
- WBS: 3.1, 3.2, 3.4, 3.5, 3.6 (mold_variant 대체 3.3은 이번 범위 아님)
- 선행 작업: T-001 (`data/lego.sqlite`의 `set_parts_flat`, `set_scope`, `sets`, `parts`, `colors`)
- 참고 문서: `docs/planning/03_아키텍처설계서.md` §8, `docs/planning/01_PRD.md` §4.3·§5·§8, `docs/planning/02_데이터수집설계서.md` §3.1·§3.2

## 목표
LLM 없이 결정적으로 동작하는 부품 매칭 엔진을 만든다. 사용자가 보유 세트(번호·수량)와 부품 보정을 등록하면 다음을 계산한다.
1. 보유 부품 합계
2. 목표 세트의 부족 부품 표
3. 부족이 가장 적은 세트 추천

결과는 이후 근거 카드(T-00x)와 UI가 그대로 쓸 수 있는 데이터 구조로 돌려준다.

## 범위
- 포함
  1. 세트 번호 정규화·검증 (없는 번호는 거부하고 유사 후보 제시)
  2. 세트 부품 조회 (`set_parts_flat` 기반)와 보유 부품 집계 (수량 곱 + 보정 delta)
  3. 부족 분석: `exact`, `ignore_color` 모드
  4. 추천: 후보 필터(범위·연도·부품 수) → 부족 계산 → 결정적 정렬 → 상위 N
  5. 사용자 컬렉션 저장소: **별도 SQLite `data/user.sqlite`** (아래 "중요" 참고)
  6. 성능 측정 스크립트
- 제외 (하지 말 것)
  - `mold_variant`(부품 관계 대체) — 다음 작업. 다만 `mode` 인자는 확장할 수 있게 두고, 지원하지 않는 모드는 `ValueError`
  - LLM 호출, Chroma, UI, FastAPI
  - `lego.sqlite` 스키마·적재 코드 수정 (T-001 산출물). 버그를 발견하면 고치지 말고 결과 보고에 적는다
  - `docs/` 아래 다른 문서 수정 (이 파일의 결과 보고만 수정)

## 중요 설계 제약
- **사용자 데이터는 `lego.sqlite`에 넣지 않는다.** `lego.sqlite`는 적재할 때마다 임시 DB로 통째로 교체되므로 사용자 데이터가 사라진다. 컬렉션은 `data/user.sqlite`(git 제외)에 둔다.
  - 경로는 settings `paths.user_sqlite: "data/user.sqlite"`로 추가한다.
  - `.gitignore`에 `data/user.sqlite`를 추가한다 (이 작업에서 허용).
- **수량 기준**: 세트의 부품 집합은 `set_parts_flat`을 그대로 쓴다 (최신 인벤토리, 스페어 제외, 미니피그 전개 — T-001에서 검증).
- **공식 부품 수와 계산값 분리**: 결과에 `official_num_parts`(= `sets.num_parts`)와 `need_total`(= 집계 합)을 **둘 다** 넣는다. 둘이 다르면 `count_mismatch=True`로 표시한다 (예: 75257-1은 1,328 vs 1,351).
- **결정성**: 같은 입력이면 항상 같은 출력이어야 한다. 정렬에는 반드시 마지막 기준으로 `set_num`을 둔다.
- 표준 라이브러리만 사용한다 (`collections.Counter`, `sqlite3`). 새 의존성 금지. 테스트에서의 독립 검증용으로만 pandas 사용을 허용한다 (`.venv`에 설치돼 있음).

## 테스트 요구사항
### 단위 (`tests/test_planner_unit.py`) — T-001 소형 픽스처를 tmp DB로 적재해 사용
- 정규화: `"A"` → `"A-1"`, 공백·하이픈 처리, 없는 번호 → `SetNotFound`와 후보
- 같은 세트 2개 보유 → 보유량이 정확히 2배
- 보정 delta: 추가(+)와 분실(−), 음수 결과는 0
- exact: 같은 부품의 다른 색은 매칭되지 않음 / ignore_color: 매칭됨
- `color_id = -1` 처리 (exact에서 항상 부족)
- 부족 계산: 손으로 계산한 기대값과 완전 일치 (`total_missing`, `lots_missing`, `coverage`, `rows`)
- 추천: 보유 세트 제외, 필터 적용, 정렬 기준(동점 처리 포함), 결정성(두 번 호출 결과 동일)
- 지원하지 않는 모드 → `ValueError`
- CollectionStore: 생성·교체·보정·조회, 다른 컬렉션과 데이터가 섞이지 않음

- 설계 판단과 이유:
  - 보유량은 수량 곱과 모든 delta를 합산한 뒤 한 번만 0으로 제한한다. 따라서 보정 이력 순서에 따라 결과가 달라지지 않으며 0 이하 키를 남기지 않는다.
  - 분석·추천은 같은 부족 계산 함수를 공유한다. exact의 Unknown(`color_id=-1`)은 보유량과 무관하게 전량 부족으로 처리하고, ignore_color는 부품 번호별로 수량을 합친다. 부족 행의 Unknown 보유량은 매칭 가능한 수량인 0으로 표시한다.
  - 추천은 메타데이터 쿼리 1회와 후보 부품 일괄 쿼리 1회만 실행한다. 후보 필터를 CTE로 재사용하여 N+1과 대량 번호의 SQL 바인딩 개수 제한을 피했다. 단위 테스트에서 SQL 2회 실행을 확인했다.
