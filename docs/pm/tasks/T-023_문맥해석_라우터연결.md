- 상태: 완료 (2026-10-23)
- 관련 요구사항: F2009·F2011(선택 후 질문 이어가기), F2010, F2007, ADR-018 ②③④⑧
- 선행 작업: T-021(`DialogueState`). **T-022와 병행 가능**(파일 겹침 없음)
- 분할 기준: Codex 1회 실행에서 테스트를 포함한 변경 파일이 15개를 넘을 것 같으면 둘로 나눈다. **T-023a**는 해석기·상태 갱신(1·2·6), **T-023b**는 정제 검색·router-v4·템플릿(3·4·5)이다.

## 목표
이전 결과를 가리키는 표현("그중", "첫 번째", "그거", "색상은 무시하면")을 **결정적으로** 해석한다. 오케스트레이터가 같은 대상·목록·모드로 답하게 하고, 다음 턴을 위한 상태 변화와 화면용 목록(`items`)을 돌려준다.

## 범위
- 포함
  1. `src/rag_service/services/context_resolver.py`(신규): `resolve_context(question, state, conn, settings) -> ResolvedContext`. 05 §3.3의 우선순위·충돌 규칙·되묻기 생성을 맡는다. 서수·지시어·"그중"·모드 사전은 `config/dialogue_cues.yaml`에 둔다.
  2. `ResolvedContext`: 대상 세트, 비교 세트, 정제 조건(`base_spec`, `allow`), 모드, 이어 실행할 pending 요청, 되묻기(`clarify`), 컬렉션 변경 대상(T-022가 쓸 `set_num`)을 담는다.
  3. `src/rag_service/db/queries.py`: `FilterSpec.set_nums: tuple[str, ...] = ()` 허용 목록(`IN`). 빈 튜플이면 기존과 같다.
  4. `src/rag_service/services/search.py`: `search_sets(..., base_spec=None, allow=None, keep_order=None)`. 새 조건은 base_spec과 AND로 합친다. 허용 목록 안에서만 찾고, `keep_order`면 원래 표시 순서를 유지한다. `SearchResult.spec`을 응답까지 전달한다.
  5. `src/rag_service/services/orchestrator.py`
     - `answer(..., context: ResolvedContext | None = None)`
     - `OrchestratorResponse`에 `items: list[dict]`(rank·set_num·name·year·num_parts·missing·lots_missing)와 `state_delta`(새 목록·대상·모드·pending)를 추가한다.
     - 추천(build)도 `items`와 `set_nums`를 채운다(현재는 표에만 있음).
     - mode는 context가 우선이고, 없으면 기존 단서를 쓴다.
  6. `src/rag_service/rag/prompts.py` router-v4: v3에 `context` 요약 필드를 더한다. `settings.router.prompt_version: router-v4`. v3는 비교용으로 남긴다.
  7. 템플릿 문장 개선(`rag/templates.py`, `rag/db_cards.py`): 핵심 1~2문장. **제작 가능 표현 규칙**(부족 0일 때만 "만들 수 있어요")을 지킨다. 카드의 "공식 부품 수"는 "부품 수(Rebrickable 기준)"로 바꾼다(색인 텍스트 `item_text.py`는 재색인이 필요하므로 **제외**, 남은 이슈로 기록).
  8. 테스트(신규 `tests/test_context_resolver.py`, `tests/test_search_refine.py`, 기존 템플릿 테스트 기대값 갱신)
- 제외: 상태 저장·트랜잭션(T-021·T-024), 컬렉션 변경 실행(T-022), API·화면

## 인터페이스 계약
```python
@dataclass(frozen=True)
class ResolvedContext:
    subject: str | None                     # 오케스트레이터 selected_set으로 전달
    subject_source: str | None              # explicit|list|card|ui|state
    compare: tuple[str, ...] = ()
    refine: dict | None = None              # {"base_spec": {...}, "allow": [...], "kind": "search"|"recommend"}
    mode: Literal["exact","ignore_color"] | None = None
    resume: dict | None = None              # pending에서 이어 실행할 요청
    clarify: dict | None = None             # {"question": str, "options": [set_num...], "kind": "target"|"quantity"}
    collection_target: str | None = None    # 컬렉션 변경 대상
    notes: tuple[str, ...] = ()             # "목록 밖 세트입니다" 같은 경고
def resolve_context(question: str, state: DialogueState, *, conn, settings) -> ResolvedContext
def answer(question, *, selected_set=None, history=None, collection_id=None, deps=None,
           on_event=None, context: ResolvedContext | None = None) -> OrchestratorResponse
```

- 설계 판단과 이유:
  - 명시 대상 > pending 선택 > 표시 목록 서수 > 지시어/현재 대상 순서를 코드로 고정했다. 이름이 여러 세트에 대응하면 대표 판본을 임의로 고르지 않고 후보를 반환한다. 새 추천은 이전 subject를 실행 대상으로 쓰지 않지만 저장된 subject는 유지한다.
  - `FilterSpec.set_nums=()`의 기존 의미는 유지한다. 서비스의 `allow=[]`는 결과 없음으로 구별한다. 단일 필드에 모두 담을 수 없는 조건도 이전 DB 결과와 교집합을 계산해 AND 의미를 보존하고, 그 제한을 `spec.set_nums`에 남긴다.
  - 검색 `spec`은 JSON 호환 딕셔너리로 응답과 상태 변경값에 전달한다. 검색·추천의 `items`, `set_nums`, `last_list.items`는 같은 표시 순서를 사용한다. 정제 0건은 이전 목록 연도를 DB 근거로 안내하며 `state_delta={}`로 상태를 유지한다. 여러 건이면 정제된 목록/spec을 유지한 채 target pending을 설정하고, 선택 응답은 선택 세트의 DB 소개로 이어진다.
  - 추천 결과 자체는 캐시하지 않는다. 컬렉션 ID가 있으면 매 요청 저장소에서 최신 보유량을 읽고, 색상 모드 후속은 대상이 있으면 분석, 대상이 없으면 저장된 추천 파라미터로 재계산한다. 추천 정제의 부족 수량도 planner로 계산한다.
  - `TemplateAnswer.items`를 추가해 추천 계산을 중복 실행하거나 표의 표시 문자열을 역파싱하지 않는다. 이에 따라 DB CLI JSON에도 `items`가 추가된다. 부족이 양수이면 조건부 완성 문구만 쓰고, 0일 때만 "지금 가진 부품으로 만들 수 있어요"를 사용한다.
  - router-v4는 v3 경계 규칙과 출력 스키마를 유지하고 사용자 메시지에 문맥 요약을 추가한다. 기존 전체 메시지 해시 캐시를 그대로 사용하므로 요약이 달라지면 캐시가 분리된다. 수치 사후 검증·인용 필터·2노드 그래프 구현은 변경하지 않았다.
  - `state_delta`는 저장할 필드의 교체값이다. 키 생략은 유지, `pending=None`은 해제를 뜻한다. `turn_id`는 아직 저장 전이므로 `None`이며 T-024가 실제 턴 ID를 채워 원자 저장해야 한다. 추천 `rec.scope`는 T-021의 문자열 계약에 맞춰 범위 목록을 쉼표로 연결하고 재계산 시 복원한다. `ResolvedContext.resume`·`collection_target`만 전달하며 컬렉션 변경은 실행하지 않는다.
