## 목표
"2018년 이후 나온 1,000개 이상인 우주선" 같은 자연어 조건을 다음 흐름으로 처리한다.
1. **Filter 프롬프트**가 조건을 JSON(`FilterQuery`)으로 추출한다.
2. **SQL**이 수치·이름 조건으로 후보를 거른다.
3. **set_meta 유사도**로 의미 조건(우주선·지상 탈것) 순서를 정한다.
4. **LLM 검수**가 의미 조건을 어긴 후보를 뺀다.
5. **세트 카드 목록**을 돌려준다.

카드를 고르면 그 세트로 대화가 이어진다 (화면 연결은 M5, 이번에는 결과에 세트 번호 목록을 담는다).

## 설계 (검토 포인트 ①~⑥)

### ① Filter 프롬프트 규칙
- 출력 키(프롬프트에 그대로 명시): `year_from`, `year_to`, `parts_min`, `parts_max`, `subtheme`, `minifig`, `name_keywords`, `exclude_keywords`, `semantic`, `sort`, `order`, `limit`
- 규칙
  - `name_keywords`는 **사용자가 세트명에 들어갈 단어를 명시했을 때만** 쓴다 (예: "팔콘 들어간 세트" → `["Falcon"]`). 의미 조건(우주선·탈것·작은)은 `semantic`에만 넣는다.
  - `subtheme`은 UCS일 때만 `Ultimate Collector Series`다.
  - 연도 "이후·부터"는 이상, "이전·까지"는 미만·이하를 구분한다 (예: "2010년 이전" → `year_to` 2009).
  - 미니피그·키워드는 영어로 쓴다. 한국어 이름은 별칭 사전(`ko_aliases`)으로 먼저 바꿀 수 있으면 바꾼다 (예: 루크 → Luke Skywalker).
- 몇 개 예시(few-shot)를 프롬프트에 넣는다 (실측 4문항 기반).

### ② 0건 처리 — 완화하지 않음 (사용자 결정) + 추출 조건 검증
- SQL 결과가 0건이면 **조건을 풀지 않고** "조건에 맞는 세트가 없습니다"를 안내한다 (`no_result=True`).
- 대신 LLM이 질문에 없는 조건을 만들어 0건이 되는 것을 막기 위해, **추출 직후 결정적 검증**을 한다 (실측: "우주선" → `name_keywords ["Star","ship"]`).
  - `name_keywords`·`exclude_keywords`의 각 단어는 다음 중 하나여야 한다. 어긋나는 단어는 버리고 `warnings`에 기록한다.
    - (a) 질문 원문에 대소문자 무시로 그대로 있음
    - (b) 질문 원문의 한국어 토큰이 `ko_aliases`(verified 여부 무관)로 그 영어 단어를 포함하는 정식명에 대응함
  - `minifig`도 같은 규칙이다. 질문에 이름이 없으면 버린다.
  - 수치 조건은 질문에 숫자(아라비아 숫자 또는 "천" 같은 한글 수사)가 있을 때만 받아들인다. 없는데 들어오면 버린다.
- 테스트
  - 질문에 없는 `name_keywords`가 제거된다.
  - 별칭 대응(팔콘 → Millennium Falcon → `Falcon` 허용)
  - 숫자가 없는 질문에서 수치 조건이 제거된다.
  - 0건이면 `no_result` 안내와 완화 없음

### ③ 의미 정렬과 검수 대상
- `semantic`이 있을 때만 의미 정렬을 한다.
  - SQL 후보(최대 `search.sql_candidate_limit`, 기본 300) 안에서 `set_meta` 유사도를 계산한다 (Chroma `where={"set_num": {"$in": ids}}`).
  - 상위 `search.review_top_n`(기본 20)개를 검수 대상으로 한다.
- `semantic`이 없으면 의미 정렬과 LLM 검수를 생략하고 SQL 결과를 그대로 쓴다 (예: "UCS 중 2010년 이전").
- 의미 정렬 질의 = `semantic` 영어 + 원 질문 (T-005 교훈: 영어 질의 정밀도가 높다).

### ④ LLM 검수 (`review-v1`)
- 입력: 원 조건 문장, `semantic`, 후보 목록(`id`, 세트명, 연도, 부품 수, 관련 엔티티 `set_entities`, 미니피그 수)
- 출력: `{"keep": [id...], "drop": [{"id", "reason"(≤20자)}]}`, JSON 키를 프롬프트에 명시한다.
- 규칙
  - 의미 조건에 명백히 맞지 않는 후보만 뺀다 (예: "지상 탈것"에서 피규어·흉상·비행체 제외).
  - 판단이 애매하면 남긴다.
  - **수치 조건은 판단하지 않는다** (이미 SQL이 보장한다).
- 실패하면(파싱 실패·타임아웃) 검수 없이 의미 정렬 결과를 쓰고 `warnings`에 남긴다.
- `drop` 사유는 결과 객체에 보관한다. 화면 노출 여부는 M5에서 정한다.

### ⑤ 최종 정렬과 개수
- 사용자가 정렬을 명시하면(`sort` 키가 질문에서 추출되었을 때, 예: "최신순", "부품 많은 순") 그 순서를 따른다.
- 명시하지 않았으면 의미 정렬 순서, 의미 조건이 없으면 연도 오름차순이다.
- 표시 개수는 `limit`(기본 `search.result_limit` 12)이다.
- 결과 = T-009 `answer_filter` 형식(`TemplateAnswer`) + `set_nums`(카드 선택용) + `no_result` + `review`(keep/drop 수와 사유 — 화면은 "의미 조건에 맞지 않는 N개 제외 ▸" 펼치기)

### ⑥ 진행 상태·캐시·지연
- 진행 이벤트: `extracting → querying → ranking → reviewing → done`
- LLM 응답 캐시: Filter·검수 응답을 T-007 `llm_cache`에 버전 키로 저장한다. 같은 조건 문장의 2회차는 LLM 호출 0회다.
- 지연 목표: 첫 실행 ≤ 6초 (추출 약 1.3초 + 임베딩 + 검수 약 2초 [추정]), 캐시 적중 ≤ 1초
