# T-022 대화 기반 컬렉션 변경과 중복 실행 방지

- 상태: 완료 (2026-10-23)
- 관련 요구사항: F2010(보유 세트 기반 추천의 입력), PRD B-01·B-08, ADR-018 ⑤
- 선행 작업: T-021(`collections.version` 열·`collection_events` 테이블). **T-023과 병행 가능**(파일 겹침 없음)

## 목표
대화 표현을 컬렉션 변경 의도로 결정적으로 해석한다. 검증·원자성·멱등을 지키며 반영하고, 변경 전후 수량을 돌려준다. 이 작업은 서비스 함수까지이고, 채팅 흐름 연결은 T-024에서 한다.

## 표현 의미 (05 §4.1 고정)
| 예 | intent | op | qty |
|---|---|---|---|
| "75301 하나 등록해줘", "75301 두 개 있어" | own | set | 1 / 2 |
| "그거 하나 더 추가해줘" | own | add | +1 |
| "실제로는 두 개야", "3개로 바꿔줘" | own | set | 2 / 3 |
| "그거 보유 목록에서 빼줘", "삭제해줘" | own | remove | — |
| "그거 가지고 싶어", "사고 싶어" | wish | none | — |
| "그거 하나 있어"(보유 진술) | own | set | 1 (기존 qty>1이면 `needs_confirm`) |

## 범위
- 포함
  1. `config/collection_intents.yaml`(신규): 동사 패턴(등록·추가·더·빼·삭제·제거·바꿔·있어·가지고 있어), 소망 패턴(갖고 싶·사고 싶·살까), 부정어(없어·안 가지고), 한국어 수량(하나·한·두·둘·세·셋·네·넷·다섯…열, 숫자+개)
  2. `src/rag_service/services/collection_actions.py`(신규)
     - `parse_intent(question) -> CollectionIntent | None`: 대상은 다루지 않고 동사·수량만 본다.
     - `apply(uid, *, set_num, op, qty, request_id) -> ActionResult`
     - `describe(result) -> str`: 템플릿 문장
  3. `src/rag_service/planner/collections.py`: `apply_change(cid, set_num, op, qty, request_id)`를 `BEGIN IMMEDIATE` 한 트랜잭션으로 처리한다. events 조회(멱등) → 현재 수량 → 계산 → 반영(0이면 행 삭제) → events 기록 → `version += 1`. `get()`이 `version`을 함께 돌려준다.
  4. `src/rag_service/services/users.py`: `save_collection(uid, sets, expected_version=None)`. 버전이 다르면 `CollectionConflict`, 전체 교체도 events(op=`replace`)에 기록한다.
  5. `config/settings.yaml`: `collection.max_qty: 99`
  6. 테스트(신규 `tests/test_collection_actions.py`)
  7. **선행 정리 (T-021 리뷰에서 넘어온 것)**
     - `CollectionStore.create()`: `INSERT INTO collections(id) VALUES (?)`로 열을 명시한다(이관 뒤 `version` 열 호환). 회귀 테스트를 추가한다.
     - `tests/test_mmr.py`: 실제 Chroma를 쓰는 테스트가 운영 `data/chroma`에 쓰지 않도록 `paths.chroma_dir`를 `tmp_path`로 분리한다. DoD에 "전체 테스트 뒤 `git status data/`가 깨끗함"을 추가한다.
- 제외: 대상 해석("그거" → 세트)은 T-023, 채팅 연결·되묻기 저장은 T-024, 화면은 T-025

## 인터페이스 계약
```python
@dataclass(frozen=True)
class CollectionIntent:
    kind: Literal["own","wish"]; op: Literal["set","add","remove","none"]
    qty: int | None; statement: bool            # statement=보유 진술("하나 있어")
@dataclass(frozen=True)
class ActionResult:
    set_num: str; name: str; op: str; qty_before: int; qty_after: int
    applied: bool; replayed: bool; needs_confirm: bool; version: int
class CollectionConflict(Exception): ...
def parse_intent(question: str, settings: dict | None = None) -> CollectionIntent | None
def apply(uid: str, *, set_num: str, op: str, qty: int | None, request_id: str,
          statement: bool = False, confirm: bool = False) -> ActionResult
# - set_num은 get_set으로 존재를 확인한다(없으면 SetNotFound → 후보 안내는 호출자 몫)
# - qty: 정수 1..max_qty. add는 결과도 max_qty 이하
# - statement=True이고 기존 qty>요청 qty이며 confirm=False → 반영하지 않음(needs_confirm=True)
# - 같은 request_id 재호출 → 저장된 결과(replayed=True), DB 변화 없음
def describe(r: ActionResult) -> str
# 예: "75301-1 Luke Skywalker's X-Wing Fighter: 보유 0개 → 1개로 등록했어요."
#     needs_confirm: "지금 2개로 기록돼 있어요. 1개로 줄일까요?"
```

- 설계 판단과 이유:
  - 대상 해석은 하지 않는다. 소망은 `wish/none`, 부정·조회 질문·모호한 수량은 `None`이며, 수량이 없는 등록/추가는 임의로 1개라고 추측하지 않는다. 한국어 수량은 지정된 하나~열을 지원하고, 그 밖의 복합 수량은 부분 매칭해 오등록하지 않도록 거절한다.
  - `BEGIN IMMEDIATE` 안에서 이벤트 조회 → 현재 수량/버전 조회 → 축소 확인 판단 → 수량 반영 → 이벤트 기록 → 버전 증가를 수행한다. 확인 대기 결과는 이벤트로 저장하지 않아, 동일 요청 ID의 `confirm=True` 재호출이 실제 변경을 수행할 수 있다. 확인 대기의 `qty_after`는 적용할 제안 수량이다.
  - T-021 이벤트 스키마를 유지했다. 재생 시 현재 버전에서 해당 이벤트 이후 같은 컬렉션의 이벤트 수를 빼 최초 처리 버전을 복원한다. 중간에 다른 변경이나 전체 교체가 있어도 과거 결과의 수량·연산·버전을 반환한다. 스키마의 전역 UNIQUE 요청 ID가 다른 사용자와 충돌하면 다른 사용자의 결과를 노출하지 않고 `CollectionConflict`로 거절한다.
  - 전체 교체는 한 번 저장할 때 이벤트 1건(`op=replace`, `set_num=""`, `request_id=NULL`, 전후 총 보유 수량)과 버전 +1을 기록한다. 버전 비교와 최초 컬렉션 생성도 같은 트랜잭션 안에서 처리하며 기존 부품 보정은 보존한다.
  - 신규 컬렉션 테이블은 버전 0으로 생성한다. 이전 UI가 만든 버전 열 없는 DB는 읽을 때 버전 0으로 호환하고, 첫 변경 전에 T-021의 `migrate(path)`를 호출해 백업 후 이관한다. 기존 DB의 ALTER를 별도로 구현하지 않았다. 이 경로는 임시 DB에서만 실행했으며 운영 DB는 이관하거나 수정하지 않았다.

  - 첫 저장 시 기존 DB를 백업·이관하는 호환 경로와 `replace` 이벤트의 총수량 기록 규약을 리뷰해 주기 바란다. 후속 작업에서도 컬렉션 버전 증가와 이벤트 1건 기록을 함께 유지해야 과거 요청의 버전 재생이 성립한다.
  - 채팅 연결·되묻기 보존·대상 해석·화면/API의 버전 필드 연결은 명세대로 T-023~T-025 범위로 남겼다.
