# RAG 파이프라인 설계문서 — LEGO Archive & Build Planner

> 상세 결정 기록: `docs/pm/decisions.md`(ADR-001~018), 아키텍처: `docs/planning/03_아키텍처설계서.md`

## 1. 전체 흐름
```mermaid
flowchart LR
  Q[사용자 질문] --> CTX[문맥 해석<br/>그중·첫 번째·그거·색상 무시<br/>context_resolver]
  CTX --> R[라우터<br/>LLM router-v4 + 결정적 규칙]
  R -->|fact·set_ops·build| DB[(SQLite<br/>Rebrickable)] --> T[템플릿 답변 + DB 근거 카드]
  R -->|filter| S[조건 탐색<br/>필터 추출→SQL→의미 정렬→검수] --> C[카드]
  R -->|collection| CA[보유 목록 변경<br/>트랜잭션·멱등]
  R -->|narrative·compare·build_archive| G
  subgraph G[LangGraph 2노드]
    direction LR
    RET[retrieve<br/>메타 청크 + MMR 외부 문서<br/>질문 시점 수집 P1→위키→P2] --> GEN[generate<br/>프롬프트3 [근거 N]]
  end
  G --> V[수치 사후 검증] --> CIT[인용 필터<br/>인용 근거만 표시]
  T --> V
```
- 필수 RAG 그래프는 **retrieve → generate 두 노드**다(`rag/graph.py`, 구조 출력 `docs/screenshots/rag_graph.mmd`). DB·부품 계산 결과는 별도 노드가 아니라 state의 `injected_cards`로 주입한다.
- 라우팅·대화 상태·컬렉션 변경은 그래프 밖 서비스 계층(`services/`)이 맡는다.

## 2. Vector DB 컬렉션 구조 (Chroma)
| 컬렉션 | 내용 | 청크 단위 | ID 규칙 | 메타데이터 필드 |
|---|---|---|---|---|
| `set_meta` | 항목 메타데이터 (RAG 1) 378건 | 세트 1건 = 1청크 | `item_id`(= 세트 번호, 예 `75301-1`) | source_type=set_meta, title, item_id, item_title, theme, year, num_parts, lang |
| `set_docs` | 외부 문서 (RAG 2) 135문서 · 3,529청크 | 섹션 기준 1000자·중복 200 | `{scope}:{doc_id}:{seq}` (scope = entity·series) | source_type=wikipedia, title, url, license, doc_id(page_id), section_path, lang, entity_kind, sets(연결 세트 배열), search_query, collected_at |
- 기체·캐릭터 문서는 1벌만 저장하고, 연결 세트는 `sets` 배열에 **합집합**으로 추가한다(덮어쓰기 금지, ADR-008).
- 임베딩: `text-embedding-3-small`(GMS), 임베딩 캐시(SQLite)로 재색인 비용을 줄인다.

## 3. 수집 · 청킹 · 색인 흐름
1. **사전 수집**: 세트명 → 위키 엔티티 규칙(`config/entity_rules.yaml`, core 249/332 매핑) → 엔티티·시리즈 문서 수집 → 정제(표·각주 제거) → 청킹 → `set_docs`.
2. **질문 시점 수집**(F2003·F2004): 세트에 근거가 부족할 수 있으므로 질문마다
   - P1이 검색어(영·한)를 추출 → 위키백과 검색 → P2가 후보 선별(문서 2개·30초 예산) → 수집 → 도메인 보호 장치(제목·도입부 500자에 스타워즈·레고 단서 필수) → 청킹·색인.
   - 수집 매니페스트에 세트별 검색어·doc_id를 기록하고 이미 검색한 검색어는 건너뛴다(NF2002).
3. **외부 호출 예절**: UA에 연락처, 요청 간격, 429/5xx 재시도(NF2006).

## 4. 검색 결과 병합과 중복 제거
- 순서: DB 주입 카드 → **선택 세트 메타 청크(항상)** → 외부 문서 MMR 결과(Top-k 5).
- 중복 제거: 청크 ID와 정규화 텍스트 해시가 같으면 제외한다. 언어가 다른 같은 내용은 둘 다 유지한다.
- 근거 카드 번호는 병합 순서대로 1부터 매기고, 생성 뒤에는 실제로 인용된 번호만 화면에 남긴다.

## 5. 프롬프트 3종
| 프롬프트 | 역할 | 입력 | 출력 형식 | 실패 시 처리 |
|---|---|---|---|---|
| 1. 검색어 추출 (P1 v2.1) | 레고 스타워즈 전문가로서 위키 검색어 생성 | 세트 번호·이름, 질문 | JSON `{"queries":[{"q","lang","purpose"}]}` | 파싱 실패·빈 결과 → 세트 이름 검색어로 대체(세트 자체 문서 항상 포함) |
| 2. 후보 선별 (P2) | 검색 후보 중 세트·질문에 맞는 문서 선택 | 세트, 질문, 후보 제목·요약 | JSON `{"selected":[{"id","reason"}]}` | 실패 → 규칙 기반 대체 선택, 도메인 보호 장치로 오선택 차단 |
| 3. 답변 생성 (P3 v2) | 제공 근거만으로 답변, 핵심 1~2문장 + 항목 | 질문(해석된 대상 이름 포함), 근거 카드, 최근 같은 대상 대화 | 본문에 `[근거 N]` 인용 | 근거 없음 → "확인되지 않음", 인용 없음 → 안내, 근거 없는 숫자 문장 → 사후 검증으로 제거 |
- 구조화 출력은 GMS 실측으로 `json_mode`를 채택했다(T-004: function calling·json_schema보다 오분류가 적음).

## 6. 검색 설정과 실험 (F2014)
| 설정 | 값 | 이유 | 바꿨을 때의 차이 |
|---|---|---|---|
| 청크 크기 | 1000 | 위키 섹션 1~2개 분량, 한국어 문서가 짧아 더 줄이면 문맥 손실 | 실험 제외(로드맵 후속). 후보 풀·질의 구성이 더 큰 변수였음 |
| 중복 길이 | 200 | 섹션 경계에서 문장 단절 방지 | — |
| Top-k | 5 | 생성 입력 길이와 근거 다양성의 균형 | 3: Recall@5 −2문항 / 8: 변화 없음 |
| 검색 방식 | **MMR** (fetch_k 40, λ 0.7, 문서당 상한 없음) | 유사도 검색은 한 문서에 후보가 몰려 상한 뒤 빈자리가 생김 | 섹션 Recall@5 **0.650 → 0.875**(26 → 35/40), 한국어 문서 0.54 → 0.92 |
| 검색 질의 | 질문 원문 | P1 영어 확장어가 한국어 문서를 밀어냄(가설 검증) | 확장어 포함 대비 +5문항, 영어 문서 −1문항(수용, ADR-017) |
- 평가셋: 검색 40문항(문서+섹션 정답 라벨), 평가 스냅샷 고정, 26개 설정 비교(`eval/results/2026-10-22_t017-*`).
- MMR과 유사도 검색의 차이(대표 5문항 상위 5개 비교): `eval/results/2026-10-22_t017-compare-mmr.md`.

## 7. 근거 표시 방식
- 답변 본문의 `[근거 N]`을 파싱해 **인용된 카드만** 답변 아래 "출처 보기 (N)" 접기에 표시한다(번호·출처 유형 배지·제목·원문 링크·라이선스·발췌).
- 웹에서는 `[근거 N]`을 누르면 그 답변의 "출처 보기"가 펼쳐지고 해당 카드가 강조된다. 인용이 하나도 없으면 "답변에 인용된 근거가 없습니다".
- 수치 사후 검증이 문장을 지우면 답변 아래에 "검증되지 않은 수치를 포함한 문장 N개를 제외했습니다"를 표시한다.

## 8. 도메인 특화 기능 설계 이유
- 레고 사용자의 실제 질문은 "이 세트 부품 몇 개?"·"내 부품으로 뭐 만들 수 있어?"처럼 **정확한 숫자**를 요구한다. LLM 단독은 숫자를 지어내므로(RAG 전후 비교: 단독 1/11 정확) 숫자는 DB와 결정적 계산으로만 만든다.
- 부품 집계 정의: 최신 인벤토리, 스페어 제외, 미니피그 구성 부품 전개, `(부품 번호, 색상)` 합산 → `sets.num_parts` 331/332 재현.
- 추천 정렬: 부족 개수 → 부족 종류 → 커버리지 → 연도. 부족이 1개 이상이면 "N개만 더 있으면 완성"으로 표현하고 "만들 수 있다"는 부족 0일 때만 쓴다.

## 9. 화면 구성과 API 계약
- **Streamlit(필수)**과 **Vanilla 웹(F2013)**이 같은 서비스 함수(`services/chat.py chat_turn_v2`)를 쓴다.
- 화면(T-027 개편): 첫 화면 안내·예시 질문 + 가운데 단일 대화창 + 하단 고정 입력창 위 "지금 이야기 중" 칩 + 대화 안 카드([자세히 물어보기]·[갖고 있어요]) + 답변별 "출처 보기"·"처리 과정" 접기 + 접이식 왼쪽 메뉴(대화 기록·내가 가진 레고·이 세트 이야기 기록).
- API(FastAPI): `POST /api/conversations`, `GET /api/conversations[/{id}]`, `PATCH /api/conversations/{id}/subject`, `GET /api/sets/{set_num}/history`, `GET/PUT /api/collection`(version), `POST /api/chat`(SSE: `stage*` → `result`). 요청·응답은 `server/schemas.py` Pydantic 모델, `/docs`(OpenAPI)에 정의.
- 같은 `request_id` 재전송은 저장된 결과를 다시 보내 보유 목록 변경이 두 번 일어나지 않는다.

## 10. 선택 이유 · 겪은 문제 · 해결 과정
| 문제 | 원인 | 해결 |
|---|---|---|
| 구조화 출력 오분류 | function calling·json_schema에서 GMS 라우터 결과가 흔들림 | 150회 실측으로 `json_mode` + 프롬프트에 키·예시 명시(T-004) |
| 엉뚱한 문서 수집(Rolls-Royce Ghost, SpaceX 팰컨 9) | P2가 이름만 보고 선택 | 도메인 키워드 필터 → 원문 도입부 500자 도메인 단서 검사(T-007, T-019) |
| 답변의 근거 없는 숫자 | 생성 모델이 부품 수를 추측 | 수치 사후 검증으로 문장 제거 + 경고(T-012, 주입 위반 5/5 제거·오탐 0) |
| 검색 Recall 0.65 | 영어 확장어가 한국어 문서를 밀어냄 + 문서당 상한 뒤 빈자리 | MMR + 질문 원문 질의로 0.875(T-017, ADR-017) |
| 라우팅 과적합 | 틀린 문항을 보고 프롬프트를 고침 → 새 문항에서 효과 없음 | 숨긴 확인 문항으로 발견, 원인은 LLM 정답을 덮어쓰던 규칙 → 결정적 규칙 3개로 해결(12/12·8/8, T-019) |
| 탭 사이를 오가야 하는 대화 | 대화 키가 탭·세트에 묶이고 이전 결과를 버림 | 대화 상태(대상·표시 목록·모드·되묻기) 저장과 결정적 문맥 해석(ADR-018, T-021~T-025) |
| 등록 중복 실행 | SSE 재연결·재전송 | 요청 ID 장부 + 컬렉션 변경 트랜잭션·이벤트 기록(T-022·T-024) |
