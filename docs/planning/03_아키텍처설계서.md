## 1. 설계 원칙
1. **숫자는 계산, 서술은 근거.** 세트 번호·연도·부품 수·부족 수량은 SQL이나 알고리즘이 만든 값만 씁니다. LLM은 서술만 합성합니다.
2. **모든 근거는 카드로.** DB 결과와 문서 청크를 같은 "근거 카드" 형식으로 번호를 붙여 LLM에 넘기고, 화면에도 같은 번호로 표시합니다.
3. **LLM은 해석기, 판단은 코드.** 질문 분류·조건 해석은 LLM이 JSON으로 하고, 검증·필터·계산·정렬은 코드가 합니다.
4. **과제 필수 그래프 유지.** RAG 그래프는 `retrieve → generate` 두 노드로 둡니다(F2007). 라우팅과 계산은 그 바깥의 오케스트레이터가 맡습니다.
5. **설정으로 실험.** 청크·Top-k·검색 방식·재순위·번역 전략은 `config/settings.yaml` 값으로 바꿔 비교합니다.

## 3. 질의 처리 흐름

### 3.1 라우팅 (I-01)
| route | 판별 신호 (규칙 우선) | 처리 |
|---|---|---|
| `fact` | 세트 번호 + 속성어(부품 수·연도·미니피그) | db.queries → 근거 카드 → (짧은 템플릿 답변 또는 P3) |
| `filter` | 수치 비교어(이상·이후·미만), "찾아줘·목록" | filter_parser(LLM→JSON) → SQL → 메타 유사도 보조 정렬 → LLM 위반 제거(F2011) |
| `set_ops` | "공통·차이·겹치는 부품" + 세트 2개 | SQL 집합 연산 → 근거 카드 → P3 |
| `narrative` | 역사·특징·이유·설계 | RAG 그래프 |
| `compare` | "비교·달라졌·판본" + 기체·세트 | SQL 비교 표 → 근거 카드 주입 → RAG 그래프 |
| `build` | "부족·만들 수·내 세트" + 컬렉션 존재 | planner → 근거 카드 → 템플릿 답변 (LLM 선택적) |
| `build_archive` | build 신호 + 서술 신호 | planner → 선택 → RAG 그래프(선택 세트) |
- **2단계 분류**: ①정규식·키워드 규칙이 확신하면 확정 ②애매하면 Router 프롬프트(JSON: `route`, `set_nums`, `entities`, `confidence`)를 씁니다. confidence가 낮으면 `narrative`로 보내고 경고를 남깁니다.
- 컬렉션이 없는데 build 계열이면 "보유 세트를 먼저 등록하세요"라고 안내하고 종료합니다.

### 3.2 오케스트레이터와 필수 RAG 그래프의 관계
```
Orchestrator(services/orchestrator.py, 일반 Python 또는 상위 LangGraph)
  classify ─┬─ fact/set_ops ──► db ──► evidence cards ─┐
            ├─ build ─────────► planner ─► cards ──────┤
            ├─ filter ────────► filter_parser ► db ► cards
            └─ narrative/compare/build_archive ────────┤
                                                       ▼
                       rag_graph (F2007 필수 그래프, 2노드)
                       [retrieve] → [generate]
                         · state.injected_cards(DB 근거)를 받아 문서 근거와 병합
                                                       ▼
                                 verify(수치 검증) → citations 필터 → 응답
```
- `rag_graph`는 정확히 `retrieve`, `generate` 두 노드로 구성하고, `graph.get_graph().draw_mermaid()` 출력으로 검증 자료를 만듭니다(F2007).
- DB 근거를 그래프 안 별도 노드로 만들지 않고 **state 주입**으로 처리하는 이유는 필수 2노드 구조를 유지하면서 하이브리드 근거를 쓰기 위해서입니다 [PM].

### 3.3 RAG 그래프 상태 (State)
```python
class RagState(TypedDict):
    set_num: str | None            # 선택 세트 (F2006: 메타 청크 항상 포함)
    question: str
    history: list[dict]            # 최근 N턴 (설정값)
    injected_cards: list[Card]     # DB·planner 근거
    search_queries: list[str]      # P1 결과 (영문 확장 포함)
    cards: list[Card]              # 병합·번호 부여된 최종 근거
    answer: str
    used_card_ids: list[int]
    usage: dict                    # 토큰·지연
```
`Card = {n, source_type, title, url, license, text, item_id, doc_id, score}`

## 4. 색인 파이프라인

### 4.1 RAG 1 — `set_meta`
- 대상: `set_scope`의 core 332세트 + compare_only 세트
- 텍스트: 데이터 수집 설계서 §4.3 형식 (한국어 별칭 포함, 검수 전 별칭은 "검색어" 줄에만)
- ID = `set_num`, upsert이므로 멱등 (F2002)
- `scripts/index_items.py`가 색인 건수를 출력하고, 화면 상태 패널에 건수를 표시합니다.

### 4.2 RAG 2 — `set_docs`
```
P1 검색어 추출 → 후보 검색(Brickipedia opensearch/search, Wikipedia search)
 → P2 후보 선별(제목·요약만 보여 줌) → 선택 세트의 Brickipedia 문서는 강제 포함
 → 본문 수집(fetch_log/revid로 캐시) → 정제 → 구조 청킹 → 임베딩(해시 캐시) → upsert
```
- **청킹**: 섹션 경계를 먼저 쓰고, `RecursiveCharacterTextSplitter`(chunk_size·overlap은 설정값, 시작값 1,000/200자)로 상한을 적용합니다. 각 청크 앞에 `[{문서 제목} › {섹션}]` 머리말을 붙입니다.
- **ID** (ADR-008): 기체 문서 `entity:{doc_id}:{seq}` + 메타 `sets` 배열, 시리즈 문서 `series:{doc_id}:{seq}`, 세트 전용 문서 `{set_num}:{doc_id}:{seq}`. 검색 필터는 `{"$or": [{"sets": {"$contains": set_num}}, {"scope": "series"}]}`
- **재색인**: revid가 바뀌면 같은 `doc_id` 접두어의 청크를 지운 뒤 다시 넣습니다.
- **사전 수집**: `scripts/prefetch_docs.py`가 범위 세트 문서와 시리즈 시드 문서를 미리 색인합니다. 첫 질문 지연을 줄이기 위해서입니다(NF2001). 질문 시점 수집은 사전 수집에 없는 문서만 처리합니다.

## 5. 검색 파이프라인 (retrieve 노드)

```
입력: question, set_num, search_queries(P1), injected_cards
1) 메타 근거: set_meta[set_num] 직접 조회 (검색 없이 항상 포함, F2006)
2) 문서 후보:
   a. Vector: Chroma similarity (또는 MMR: fetch_k, lambda) — where 필터
      item_id ∈ {set_num, 'series'}  (+ compare 경로면 비교 대상 세트들)
   b. BM25: 같은 필터 범위의 청크에 대해 원 질문 + 영문 확장 질의로 검색
   c. RRF 융합: score = Σ 1/(k_rrf + rank)
3) (선택) 재순위: 상위 M개를 LLM 재순위 또는 교차 인코더 → 상위 top_k
4) 병합: injected_cards + 메타 카드 + 문서 카드, 중복 제거
   (같은 청크 ID, 그리고 정규화 텍스트 해시가 같은 청크)
5) 번호 부여: [근거 1..N] — DB 카드 → 메타 → 문서 순
```

### 검색 방식 비교와 채택
| 방식 | 기대 효과 | 비용 | 채택 |
|---|---|---|---|
| Vector (similarity) | 의미 매칭, 교차 언어 기본 성능 | 낮음 | **기준선** |
| Vector (MMR) | 같은 문서·섹션 반복 청크 감소 | 낮음 | F2014 비교 실험 |
| BM25 | 세트 번호·기체명·고유명사 정확 일치 | 낮음 (메모리 색인) | **채택 (Hybrid)** |
| Hybrid (RRF) | 두 방식 보완 | 낮음 | **기본값 후보** — 실험 후 확정 |
| LLM Rerank | 상위 정밀도 | 질의당 LLM 1회 | 실험군. 개선폭이 비용을 넘을 때만 기본값 |
| Metadata filter | 다른 세트 근거 혼입 방지 | — | **필수** |
| Graph RAG | 관계 질의 | 높음 | 비채택 (관계는 SQL이 담당, 1차 검토 §6) |

- BM25 구현: `rank_bm25`(의존성 추가 필요, 고정 버전으로 requirements에 명시) 또는 `langchain_community`의 BM25Retriever를 씁니다. 한국어 질문은 P1의 영문 확장어로 BM25를 수행합니다. 한국어 문서(위키 한)용 토크나이저는 공백 + 2-gram으로 시작합니다 [추정: 실험으로 보정].

## 6. 프롬프트 설계

| 프롬프트 | 역할 | 입력 | 출력(JSON 스키마) | 실패 시 |
|---|---|---|---|---|
| Router | 질문 유형 분류 | 질문, 컬렉션 유무 | `{route, set_nums[], entities[], confidence}` | `narrative` |
| Filter | 자연어 조건 → 필터 | 질문 | `{year_from?, year_to?, parts_min?, parts_max?, keywords[], has_minifig?, sort?}` | 키워드 검색만 |
| P1 검색어 추출 (F2003) | "레고 스타워즈 아키비스트" 역할로 외부 문서 검색어 생성 | 세트(이름·번호), 질문, 별칭 | `{queries[{q, lang, purpose}], en_terms[]}` 최대 N개 | 세트 Brickipedia 문서 + 세트명만 |
| P2 후보 선별 (F2004) | 수집할 문서 선택 | 후보 목록(제목·요약·출처) | `{selected[{id, reason}]}` | 상위 k개 기본 선택 |
| P3 답변 생성 (F2007) | 근거만으로 답변 | 근거 카드, 질문, 최근 대화 | 본문 + `[근거 N]` | — |

### P3 핵심 제약
- 근거 카드에 있는 내용만 씁니다. 근거가 없으면 "제공된 자료에서 확인되지 않습니다"라고 답합니다.
- **숫자·세트 번호·부품 번호는 근거 카드에 있는 값만 그대로 씁니다.** 계산(차이·합계)이 필요하면 DB 카드에 미리 계산된 값을 씁니다. LLM이 산술하지 않게 하기 위해서입니다.
- 주장마다 `[근거 N]`을 붙이고, 영어 근거는 한국어로 요약하되 고유명사는 원문을 병기합니다.
- 구조화 출력은 LangChain `with_structured_output`(Pydantic 스키마)을 쓰고, 파싱에 실패하면 1회 재시도한 뒤 대체 경로로 갑니다.

## 7. 근거 표시와 검증

### 7.1 인용 필터 (F2008)
- 답변에서 `\[근거\s*([\d,\s]+)\]`를 추출합니다 (실습 골격 `cited_sources` 재사용).
- 카드 범위 밖 번호는 제거하고, 인용된 카드만 화면에 표시합니다. 하나도 없으면 "인용된 근거 없음"을 안내합니다.

### 7.2 수치 사후 검증 (I-03)
```
tokens = 정규식 추출 { 세트 번호(\d{3,7}-\d+ | \b\d{4,6}\b 세트 문맥), 4자리 연도, 숫자+단위(개·종·%) }
allowed = 인용된 카드 텍스트와 DB 카드 값의 숫자 집합 (천 단위 콤마·% 정규화)
문장마다: 문장 안 숫자 ⊄ allowed → 문장 제거 + warnings에 기록
세트 번호가 DB에 없으면 → 문장 제거 + "존재하지 않는 세트 번호" 경고
```
- 이 검증이 PRD 출시 기준 "존재하지 않는 세트·부품 번호 0건"을 보장하는 장치입니다. 평가에서는 검증 전·후 위반 건수를 함께 보고합니다.

## 8. 부품 매칭 엔진 (planner/)

### 8.1 데이터 흐름
```
have(collection) = Σ_set qty_set × set_parts_flat[set]  +  adjustments(delta)
need(target)     = set_parts_flat[target]
key = (part_num, color_id)   # ignore_color 모드: key = part_num
```
`set_parts_flat`은 적재 단계에서 미리 계산합니다(최신 인벤토리, 스페어 제외, 미니피그 전개). 이 정의로 `num_parts` 재현을 확인했습니다 [확인: 331/332].

### 8.2 분석 알고리즘 (B-04)
```python
def analyze(have: Counter, need: Counter, mode) -> Result:
    have_k, need_k = rekey(have, mode), rekey(need, mode)
    missing = {k: n - have_k.get(k, 0) for k, n in need_k.items() if n > have_k.get(k, 0)}
    if mode == "mold_variant":
        missing, substitutions = apply_substitutes(missing, have_k, need_k, relations={"M","A"})
        # 대체는 '남는 보유량'(have - need 소비분)에서만 차감 → 같은 부품을 두 번 쓰지 않음
    return Result(missing=missing, total_missing=sum(missing.values()),
                  lots=len(missing), coverage=1 - total_missing / sum(need_k.values()),
                  substitutions=substitutions)
```
- `color_id=-1`은 exact 모드에서 항상 부족으로 셉니다.
- 대체 관계는 양방향으로 보되 1단계만 허용합니다. 연쇄 대체는 하지 않습니다 [PM].

### 8.3 추천 (B-06)
- 후보 = 범위 세트(필터 적용) − 보유 세트
- 벡터화: 후보별 need를 희소 행렬(후보 × 부품 키)로, have를 벡터로 둡니다. `missing = max(0, N − h)`의 행 합을 한 번에 계산합니다.
  - 규모는 332 × 7,237 [확인]이라 순수 Python Counter로도 충분하다고 봅니다 [추정]. 1초가 넘으면 NumPy·SciPy로 바꿉니다.
- 정렬: `total_missing ↑ → lots ↑ → coverage ↓ → year ↑`
- 결과마다 DB 근거 카드를 만듭니다: "세트 X: 필요 1,328 · 보유 일치 1,190 · 부족 138개(41종) · 모드 exact · 데이터 Rebrickable 인벤토리 v1"

### 8.4 결합 질의 (I-04, build_archive)
1. planner 추천 → 질문의 조건(예: "가장 오래된")을 Filter 프롬프트로 정렬 키로 해석 → 코드로 선택
2. 선택 세트 번호와 추천 근거 카드를 `rag_graph`에 `set_num`과 `injected_cards`로 전달
3. 답변은 "왜 이 세트인지(DB 근거) + 어떤 세트인지(문서 근거)"를 합성

## 10. 캐시·비용·관측
| 대상 | 캐시 키 | 저장 |
|---|---|---|
| 임베딩 | `sha256(model + text)` | LangChain `CacheBackedEmbeddings` + 로컬 파일 저장소 |
| P1·P2·Router·Filter 응답 | `sha256(prompt_version + 입력)` | SQLite `llm_cache` 테이블 |
| 외부 문서 | `(source, page_id, revid)` | `data/collected/` + `fetch_log` |
| 검색어 수집 이력 (NF2002) | `(set_num, query)` | `fetch_log` |
- 관측: LLM·임베딩 호출의 `usage_metadata`와 노드별 지연을 `observability.py`가 JSON 줄로 기록합니다 (`logs/usage.jsonl`, git 제외). 평가 스크립트가 이 로그를 집계합니다. LangSmith는 선택 사항으로, 키가 있으면 켭니다.

## 12. API·UI 연동
- API 계약은 PRD §7을 따릅니다. `POST /api/chat`은 SSE로 `stage` 이벤트를 보냅니다(`routing → db → collecting(문서 제목) → indexing → retrieving → generating → verifying → done`). Streamlit은 같은 단계를 `st.status`로 표시합니다(F2012).
- 오류는 `{error: {code, message}}`이고, 코드는 `NO_INDEX`, `NO_KEY`, `NOT_FOUND_SET`, `NO_COLLECTION`, `UPSTREAM_FAIL`, `INTERNAL`입니다. `INTERNAL`의 message는 고정 문구이고 상세 내용은 서버 로그에만 남깁니다(NF2004).

## 14. 보안·법·윤리
- 키는 `.env`에만 둡니다. API 응답에는 키 설정 여부(bool)만 넣습니다.
- LEGO.com 콘텐츠는 요청하지 않습니다(링크 문자열만 생성).
- Rebrickable CSV는 하루 1회 이하로 받습니다. 원본·SQLite·Chroma·수집 문서는 git과 제출물에서 제외하고, 재생성 스크립트를 제출합니다.
- 화면 하단과 근거 카드에 라이선스·출처를 표기합니다(NF2007). LEGO 비공식 고지도 함께 둡니다.
