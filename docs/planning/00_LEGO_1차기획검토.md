## 0. 결론 요약

| 질문 | 답 |
|---|---|
| 데이터를 확보할 수 있는가 | **예 (구조화 데이터는 충분, 설명 문서는 출처 제한 있음).** Rebrickable CSV로 세트 28,546개와 부품 구성 157만 행을 확보할 수 있습니다 [확인]. 세트별 설명 텍스트는 Brickipedia(CC-BY-SA)와 위키백과에서 얻습니다 [확인]. **LEGO.com 콘텐츠는 약관상 AI 운영 목적 사용이 금지되어 제외**합니다 [확인]. |

| 핵심 실측 발견 | 스타워즈 세트 3개를 보유했다고 가정한 시뮬레이션에서 **색상까지 일치하며 100% 조립 가능한 공식 세트는 0개**였습니다 (3회 반복) [확인]. 따라서 B의 현실적인 가치는 "완성 가능 목록"이 아니라 **"부족 부품이 가장 적은 목표 + 정확한 부족 목록"** 입니다. |

## 1. 결합 서비스의 핵심 가치

### 대안 비교
| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A만 (Archive) | 시리즈·제품 지식 RAG | 구현이 단순 | 위키·Brickipedia를 검색하는 것과 차별점이 약함 |
| B만 (Planner) | 보유 부품 기반 조립 분석 | 정확한 연산 가치 | Rebrickable Build와 기능이 거의 겹침 [검색]. RAG 요소가 약함 |
| **A+B 결합** | 보유 정보를 문맥으로 삼아 지식 질문에 답하고, 추천 결과를 지식으로 설명 | 두 서비스만으로는 답할 수 없는 **복합 질문**을 처리 | 질문 라우팅과 결과 통합 설계가 필요 |

### 결론 [PM]
핵심 가치는 다음 한 문장입니다. **"내 컬렉션이라는 사실(DB)과 레고의 역사·설계 지식(문서)을 섞어 묻고, 숫자는 계산으로 이야기는 근거로 답한다."**

결합해야만 답할 수 있는 대표 질문은 다음과 같습니다.
- "내 세트들로 부족 부품 20개 이하로 만들 수 있는 스타워즈 세트 중 가장 오래된 것은? 그 세트는 어떤 특징이 있어?" → 부품 연산 → 정렬 → 문서 RAG
- "가지고 있는 75257 팔콘과 75375 팔콘은 무엇이 다르고, 공통 부품은 몇 종이야?" → SQL 집합 연산 + 문서 RAG 비교

## 3. 기존 서비스 비교와 차별화

| 서비스 | 이미 해결하는 것 | 해결하지 못하는 것·한계 | 근거 |
|---|---|---|---|
| LEGO.com (한국 포함) | 공식 제품 정보, 조립 설명서 | 단종 세트 맥락이 적음. 보유 세트 분석 없음. **AI 목적 콘텐츠 이용 금지** | [확인] 약관 원문 |
| Rebrickable | 세트·부품 DB, 컬렉션 관리, **Build(보유 부품으로 만들 수 있는 세트·MOC, 매칭률, 색상 민감도 옵션)** | 영어 UI. 수치 중심이라 "왜/어떤 특징" 설명 없음. MOC 데이터 자동 수집 금지 | [검색] |
| Brickset | 세트 메타·리뷰·컬렉션 | API는 키당 하루 100회 수준(초기값). 카피 사이트 금지 | [검색] |
| Brickipedia (Fandom) | 세트별 문서(배경·구성·특징) | 질의응답·개인화 없음 | [확인] 문서 존재 |
| ChatGPT 등 범용 LLM | 자연어 설명 | **세트 번호·부품 수·연도 환각**, 보유 정보 미반영, 출처 없음 | [추정] F2015에서 실측 예정 |

### 6가지 질문에 대한 답
1. **기존 서비스가 해결하는 것**
   - 제품 조회와 부품 목록은 LEGO.com·Rebrickable이 해결합니다.
   - 보유 부품 기반 매칭률 계산은 Rebrickable이 해결합니다.
   - **이것들을 다시 만드는 데 가치를 두지 않습니다.**
2. **새로운 가치**
   - 보유 분석과 지식 설명을 한 질문으로 처리합니다.
   - 한국어 질문에 영어 원문 근거로 답합니다.
   - 판본(같은 기체) 간 비교를 숫자와 서술 모두 근거와 함께 보여 줍니다.
3. **ChatGPT와의 차이**
   - 존재하는 세트·부품만 다룹니다 (DB 검증).
   - 사용자 보유 상태를 반영합니다.
   - 모든 수치와 서술에 출처가 붙습니다.
4. **결합의 이점**
   - 추천 결과("부족 12개로 만들 수 있음")에 "이 세트는 어떤 판본이고 무엇이 특징인지"가 붙습니다. 그래서 다음 행동(구매·조립)을 정하기 쉬워집니다.
5. **자연어가 필터 UI보다 나은 상황**
   - 조건이 복합적이거나 모호할 때: "UCS 아닌 것 중 오래된 것", "우주선 종류"
   - 비교·이유 질문: "왜 2017년판 팔콘은 부품이 많아?"
   - 보유 정보를 섞은 질문
   - 반대로 **단순 필터(연도·부품 수)는 UI 필터가 더 낫습니다.** 이 경우는 자연어를 구조화 필터로 변환해 같은 SQL로 처리하고, 화면에 적용된 필터를 보여 줍니다.
6. **독창적이면서 구현 가능한 최소 기능**
   - "보유 세트 기반 부족 부품 최소 추천 + 추천 세트의 근거 기반 설명 + 같은 기체 판본 비교"
   - 이 세 가지를 하나의 질의 라우터로 연결한 것

### 결론 [PM]
차별화는 **"통합·설명·신뢰성(출처와 수치 검증)·한국어"** 네 축입니다. 기능 개수로 경쟁하지 않습니다. 이 결합 자체도 Rebrickable이 기능을 추가하면 따라잡을 수 있으므로, 평가 지표(§9의 정확도·근거 유효성)로 품질 우위를 입증하는 데 집중합니다.

### 결론 [PM]
- **"구조화 데이터 = Rebrickable", "서술 문서 = Brickipedia + 위키백과", "LEGO 공식 = 링크만"** 의 3단 구조로 갑니다.
- 원래 지시서의 출처 후보 중 **LEGO 공식 사이트·한국 공식 사이트·공식 설명서·공식 아티클은 약관상 RAG 데이터로 쓸 수 없습니다.** 그래서 데이터 수집 계획을 위와 같이 바꿀 것을 제안합니다.

## 6. RAG와 부품 매칭 알고리즘의 역할 구분

| 질문 유형 | 예시 | 처리 경로 | 이유 |
|---|---|---|---|
| 사실 조회 | "75192 부품 수는?" | **SQL** | 정확한 값이 DB에 있음. RAG는 환각 위험만 늘림 |
| 조건 필터 | "2018년 이후 1,000개 이상 스타워즈" | **LLM → 구조화 필터(JSON) → SQL** | 수치 조건은 결정적으로 처리. LLM은 해석만 |
| 집합 연산 | "두 세트의 공통 부품" | **SQL** (part_num+color_id 교집합) | 정확한 연산 |
| 서술·역사·특징 | "테크닉의 발전 과정", "UCS 팔콘의 특징" | **RAG** (Brickipedia·위키) | 서술형 지식은 문서에만 있음 |
| 비교 | "팔콘 연도별 차이" | **SQL(연도·부품 수·미니피그) + RAG(설계 변화 서술)** | 수치와 서술을 분리해 합성 |
| 조립 분석 | "부족한 부품?" | **부품 매칭 알고리즘** | LLM 추론을 쓰지 않음 (지시서 4.4) |
| 결합 | "만들 수 있는 것 중 가장 오래된 것과 특징" | **알고리즘 → SQL 정렬 → RAG** | 단계별로 신뢰 가능한 근거 사용 |

### Graph RAG 검토
- 세트–부품–테마–미니피그 관계는 이미 **관계형 테이블과 조인으로 정확히 표현**됩니다 (inventory_parts, part_relationships, themes.parent_id) [확인: 스키마].
- "공통 부품", "같은 테마의 계보" 같은 질문은 SQL로 충분합니다.
- 문서 간 관계 추론(Graph RAG의 커뮤니티 요약 등)이 필요한 질문은 MVP 시나리오에 없습니다.
- **결론: MVP에서는 채택하지 않습니다.** 확장 단계의 "관계 그래프 시각화"는 SQL 결과를 그래프로 그리면 되므로 Graph DB도 필요 없습니다 [PM].

### 통합 원칙 [PM]
1. 숫자·세트 번호·부품 번호는 **DB 결과에서만** 가져옵니다. DB 결과도 근거 카드(`source_type=db`, 출처 Rebrickable)로 번호를 붙여 LLM에 넘깁니다.
2. LLM은 서술을 합성하고 근거 번호를 인용합니다.
3. **사후 검증**: 답변 안의 숫자·세트 번호가 근거 카드에 있는지 정규식으로 대조합니다. 없으면 해당 문장을 제거하거나 경고합니다.

### 구성도
```
[수집 계층]  Rebrickable CSV(일 1회) ─┐   Brickipedia API ─┐   Wikipedia API ─┐
                                       ▼                    ▼                  ▼
[정규화]     식별자 표준화(set_num, part_num+color_id) · 중복 제거 · 출처/라이선스 메타
                                       ▼                    ▼
[저장 계층]  SQLite (sets, themes, parts, colors, inventories, inventory_parts,
             part_relationships, user_collections, ko_aliases)
             Chroma (set_meta 컬렉션 = 항목 텍스트 / docs 컬렉션 = Brickipedia·위키 청크)
                                       ▼
[질의 처리]  LangGraph: classify → (sql | build_plan | retrieve) → generate → verify
             · 필수 검증용 retrieve→generate 2노드 그래프를 별도로 유지 (F2007)
[부품 분석]  inventory 집계 → 목표 필요량 → 부족량 → 순위 (순수 Python/SQL, LLM 없음)
[서비스]     FastAPI REST ─ Vanilla JS 화면(F2013) / Streamlit(필수 UI)
```

### 부품 매칭 알고리즘 초안
- **보유량**: 각 보유 세트의 최신 인벤토리를 쓰고 `is_spare` 부품은 제외합니다. 미니피그 구성 부품은 `inventory_minifigs`로 전개합니다. 보유 수량 N이면 곱합니다.
  - 사용자 보정(분실·추가 부품)은 차분(delta) 테이블로 반영합니다.
  - 키는 `(part_num, color_id)`이고 합산으로 중복 계산을 막습니다.
- **필요량**: 목표 세트도 같은 방식으로 계산합니다.
- **부족량**: `missing[k] = max(0, need[k] − have[k])`
- **매칭 모드**
  - `exact`(기본)
  - `ignore_color`
  - `mold_variant` (part_relationships의 M(몰드 변형)·A(대체)만 허용, P(인쇄)는 기본 불허)
  - 관계 유형 분포는 P 30,168 · R 2,988 · B 1,571 · A 1,189 · M 1,161 · T 462 [확인]
  - **대체를 적용한 결과는 항상 "대체 사용" 표시와 함께 별도 수치로 보여 줍니다.**
- **순위**: 부족 부품 총수 → 부족 종류 수 → 커버리지(%) → 연도. 사용자 조건(테마·연도·부품 수)으로 필터한 뒤 계산합니다.
- **설명서 상태**: 공식 세트만 대상으로 하고 LEGO 설명서 페이지 링크를 붙입니다. 오래된 세트는 링크 존재를 확인하지 못하면 "설명서 미확인" 배지를 붙입니다.
- **실측 근거** [확인]: 보유 3세트(862~1,237개 부품)로 스타워즈 목표 816세트를 계산했습니다.

  | 매칭 기준 | 100% 조립 가능 | 90% 이상 | 75% 이상 | 부족 20개 이하 |
  |---|---|---|---|---|
  | 색상 일치 | 0 | 0 | 0 | 7~11세트 (주로 소형 프로모) |
  | 색상 무시 | 0 | 0~1 | 3~21 | 70~97 |

  → 기본 모드로는 "완성 가능"을 약속할 수 없으므로 **부족 부품 최소 순위**를 핵심 UX로 둡니다.

## 8. 한국어·영어 처리 전략

| 대안 | 검색 성능 | 비용 | 유지보수 | 판단 |
|---|---|---|---|---|
| ① 원문 유지 + 다국어 임베딩만 사용 (교차 언어 검색) | 고유명사·세트명에서 정밀도 저하 위험 [추정] | 최저 | 최고 | 기준선 |
| **② 원문 유지 + 질의 번역·확장** (프롬프트1에서 한국어 질문 → 영어 키워드·세트명 + 별칭 사전) | 고유명사 일치 개선 [추정] | 질의당 소량 LLM 호출 (캐시 가능) | 높음 | **권장 기본** |
| ③ 전체 문서 사전 번역 후 색인 | 한국어 질의 매칭은 좋음 | 332세트×약 4KB ≈ 1.3MB 텍스트 [확인: 표본 기준 추정치]의 번역 비용, 갱신 때마다 재번역 | 낮음. 번역 오류가 근거를 오염시킴 | 비채택 (실험 비교군으로만) |

- **한국어 이름 매핑**
  - 공식 한국어 제품명 출처가 없으므로 [확인], 지어낸 "공식 한국어명"은 쓰지 않습니다.
  - 대신 **별칭 사전**(`ko_aliases`: 밀레니엄 팔콘 → Millennium Falcon, X-윙 → X-wing …)을 둡니다. 위키백과 언어 간 링크(langlinks)로 자동 후보를 만들고 사람이 검수합니다.
  - 화면에는 영문 공식명과 한국어 별칭을 함께 표시합니다.
- **토큰·비용**
  - LLM·임베딩 호출의 `usage_metadata`를 수집해 질의당 토큰·지연을 기록합니다.
  - 임베딩은 콘텐츠 해시로 캐시합니다.
  - 프롬프트1·2 응답과 위키 수집 결과도 캐시합니다 (NF2002).
  - 근거 수 Top-k와 청크 크기는 설정으로 두고 비용과 정확도의 트레이드오프를 실험합니다.

| Rebrickable 데이터 변경 | 낮음 | 재색인 | 일 1회 다운로드 + 해시 비교 증분 갱신 |

### B 데이터·권한을 못 얻을 때의 축소안
1. **축소 1**: Rebrickable CSV는 확보했지만 대체 관계가 불충분한 경우 → `exact`/`ignore_color` 모드만 제공합니다.
2. **축소 2**: 인벤토리를 쓸 수 없는 경우 → "부품 수·부품 종류 기반 근사 비교"로 낮추고, 결과에 "근사치"를 명시합니다.
3. **축소 3**: B를 "두 세트 공통 부품·차이 분석"(SQL)으로 한정하고 추천은 제외합니다.

## 12. 평가 설계 개요 (상세는 PRD 단계에서)
| 대상 | 데이터셋 구축 | 정답 검증 |
|---|---|---|
| RAG 검색 | 세트 문서에서 질문 생성(LLM 초안 → 사람 검수) 60~100문항, 한국어·영어 쌍 | 정답 청크 ID 라벨 → Recall@K, MRR, nDCG |
| 답변 | 같은 문항의 참조 답변 | 정확도 판정 (LLM 판정 + 표본 수작업), Faithfulness, 인용 정확도 |
| 부품 분석 | 수작업 소형 인벤토리 + 실제 세트 조합 시나리오 | **결정적 정답** (독립 구현 또는 pandas로 계산한 기대값과 비교) — 집계·부족 수량·색상·중복 처리 |
| 통합 | 질문 유형별 라우팅 라벨 세트 | 경로 정확도, 답변 수치와 DB의 일치율, 존재하지 않는 세트·부품 생성 0건 |

## 13. 최종 평가

- **RAG 프로젝트로서의 기술적 가치**: 충분합니다.
  - 단순 문서 QA가 아닙니다. ①질문 라우팅(SQL·알고리즘·RAG) ②DB 수치를 근거로 승격하는 하이브리드 근거 체계와 수치 사후 검증 ③교차 언어 검색 실험 ④Hybrid·Rerank 정량 비교가 있어 학습·평가 요소가 많습니다.
  - 단, **서술 문서 출처가 Brickipedia·위키로 한정**되는 것이 RAG 쪽 깊이의 상한입니다.
- **기존 서비스와의 차별화**: 계산 기능은 차별점이 아닙니다(Rebrickable과 중복). 차별화는 **"보유 사실 + 근거 있는 지식 설명 + 한국어 + 출처 추적"을 한 질문에서 제공**하는 데서 나옵니다. 이 차별화는 §9 평가 지표로 입증해야 합니다.
- **가장 큰 불확실성**
  1. Fandom 약관 (Brickipedia 사용 가능 범위)
  2. 사용자가 "부족 N개" 결과를 가치 있게 느끼는지 (사용성 검증 필요)
