# 대화 중심 챗봇 UX 설계 (v1, 2026-10-22)

> 근거 결정: ADR-018. 작업지시서: T-021~T-026.
> 이 문서는 M5에서 만든 "탭 3개 + 세트별 대화"(ADR-015)를 **한 대화 안에서 검색·질문·보유 등록·추천이 이어지는 챗봇**으로 바꾸는 설계다.
> 사용자가 확정한 방향(한 대화 중심)은 다시 묻지 않는다. 나머지는 권장안을 기본값으로 둔다.

---

## 1. 현재 구현과 목표 경험의 차이

기능은 M1~M6에서 모두 구현되어 있다. 하지만 **기능끼리 대화로 이어지지 않는다**. 실측한 차이는 다음과 같다(2026-10-22 코드 기준, T-020 커밋 a864526).

| 목표 경험 | 현재 동작 | 원인 위치 |
|---|---|---|
| 세트를 고르지 않고 첫 질문 | 웹은 첫 core 세트를 강제로 선택한다. 질문은 thread(탭/세트)에 묶인다 | `web/js/app.js start()`, `web/js/state.js currentThread` |
| "그중 2021년에 나온 건?" | 이전 검색 조건과 결과를 버린다. `search_sets(question)`은 질문만 받고, `FilterSpec`에는 세트 허용 목록이 없다 | `orchestrator._dispatch(filter)`, `services/search.py search_sets`, `db/queries.FilterSpec` |
| "첫 번째 건" | 서수를 해석하지 않는다. 추천 목록은 `set_nums`에 없고 표(`tables`)에만 있다 | `services/resolve.py`, `_dispatch(build)` |
| "그거" | 하드코딩 단어가 늘 **UI 선택 세트**를 가리킨다 | `resolve.py` 지시어 목록 |
| 대화 문맥 | 라우터는 직전 1턴의 질문·답변만 받는다. `history_for`가 route를 버린다 | `conversations.history_for`, `prompts.router_messages` |
| 채팅으로 보유 등록 | 불가. 전체 교체 `PUT /api/collection`만 있고 멱등·버전이 없다 | `users.save_collection`, `server/main.py` |
| "색상은 무시하면?" | 단서 문자열 일치에서 놓친다("색상은 무시"는 "색상 무시"와 다름) | `settings.router.ignore_color_cues` |
| 되묻기 이어받기 | `needs_input`이 일반 턴으로 저장될 뿐 다음 답과 연결되지 않는다 | `orchestrator._candidates`, `chat.chat_turn` |
| F2009 | thread=세트 번호로 분리를 충족한다. 다수 테스트가 이 키에 의존한다 | `tests/test_conversations.py` 외 |

**재사용할 자산**
- `CollectionStore`(원자적 교체·`ensure`), `planner.recommend/analyze`(결정적 정렬)
- `search_sets` 파이프라인(추출·검증·SQL·의미 정렬·검수), `resolve_sets`, `_rules`(T-019 결정적 규칙)
- `orchestrator.answer`의 경로별 템플릿·RAG(2노드)·수치 사후 검증
- SSE 작업 스레드·끊김 처리(`server/main.chat_response`), `StageTracker`, 근거 패널·최소 렌더러(`web/js/render.js`)

## 2. 권장 대화 UX

### 2.1 화면
```
┌ 헤더: 서비스명 · 상태 배지 · [새 대화] ─────────────────────────┐
│ [보조 패널]        │ 현재 대상: 75301-1 Luke's X-Wing  [변경][해제] │ [근거 패널] │
│ · 대화 목록        │ ─────────────────────────────────────────── │  [근거 N]   │
│ · 내 컬렉션        │  사용자: 루크가 들어 있는 엑스윙 찾아줘          │  카드        │
│ · 세트별 기록      │  답변: 조건에 맞는 세트 4개 ① ② ③ ④ (카드)      │             │
│   (F2009)          │        [이 세트로 질문] [보유 등록]              │             │
│                    │  ▸ 상세 표 (펼치기)                              │             │
│                    │ [ 질문 입력 ……………………………………… 보내기 ]          │             │
└────────────────────┴──────────────────────────────────────────────┴─────────────┘
```
- **탭이 없다.** 기본 화면은 하나의 대화창이고, 세트를 선택하지 않아도 질문할 수 있다.
- **현재 대상 바**: 지금 대화가 가리키는 세트를 보여 준다. [변경]은 세트 검색 상자를 열고, [해제]는 대상을 비운다.
- **대화 안 카드**: 검색·추천·후보 결과를 번호 배지(①②③)가 달린 카드로 보여 준다.
  - [이 세트로 질문]을 누르면 화면 이동 없이 현재 대상만 바뀐다(F2011 "선택하면 그 항목 질문을 이어감").
  - [보유 등록]은 대화 입력 없이도 같은 등록 서비스를 호출한다.
- **답변 구성**: 핵심 1~3문장 → 경고 한 줄 → 카드 → "상세 표"(접힘) → 처리 정보(접힘). `[근거 N]`과 근거 패널은 그대로 둔다.
- **보조 패널**: 대화 목록(여러 대화, [새 대화]), 내 컬렉션(편집기 유지), **세트별 기록**(F2009, §5).
- 좁은 화면에서는 보조 패널을 버튼으로 열고, 근거는 답변 아래에 둔다(T-015 반응형 유지).

### 2.2 답변 문장 원칙 (LLM 추가 없음)
- 사실·집합·제작 경로는 계속 **결정적 템플릿**으로 답한다. 문장만 읽기 쉽게 고친다.
  - 예: "75301-1 Luke Skywalker's X-Wing Fighter의 부품은 {num_parts:,}개(Rebrickable 기준)예요. [근거 1]" (숫자는 항상 DB 값)
- **제작 가능 표현 규칙**
  - 부족 0개일 때만 "지금 가진 부품으로 만들 수 있어요"라고 쓴다.
  - 부족이 1개 이상이면 "N개(M종)만 더 있으면 완성할 수 있어요"라고 쓴다. 테스트로 고정한다.
- 근거 카드의 "공식 부품 수" 표기는 "부품 수(Rebrickable 기준)"로 통일한다(T-020 후속).

### 2.3 대표 시나리오 (최우선, 탭 이동·번호 재입력 없음)
| # | 사용자 입력 | 해석 (상태 기준) | 실행 | 답변 형태 | 상태 변화 |
|---|---|---|---|---|---|
| 1 | 루크가 들어 있는 엑스윙 찾아줘 | 새 조건 검색 | `search_sets` (minifig·이름 조건) | 요약 + 카드 ①~⑤ | `last_list={kind:search, spec, items:[…표시 순서]}` |
| 2 | 그중 2021년에 나온 건? | "그중" → 목록 정제 | `search_sets(base_spec=spec, allow=items)` + year=2021 | 1건이면 대상 지정 + 짧은 소개 / 여러 건이면 후보 카드 + 되묻기 | 1건: `subject=그 세트(source=list)`. 여러 건: `last_list` 교체(정제 결과), `pending={kind:target}` |
| 3 | 부품이 몇 개야? | 속성 질문 + 현재 대상 | fact 템플릿(DB) | "…부품은 N개예요 [근거 1]" | 변화 없음 |
| 4 | 그거 하나 보유 목록에 등록해줘 | 지시어=현재 대상, 등록·수량 1 | `collection_actions.apply(set, qty=1, request_id)` | "75301-1 … 보유 0개 → 1개로 등록했어요" | 컬렉션 version+1, `turn.kind=action` |
| 5 | 내 부품으로 다른 건 뭐 만들 수 있어? | 추천(대상 불필요) | `recommend`(**최신 컬렉션** 다시 읽기, 보유 세트 제외) | 요약 + 카드 ①~⑤(부족 N개 배지) | `last_list={kind:recommend, rec:{mode:exact,…}, items}` (subject 유지) |
| 6 | 첫 번째 건 어떤 기체야? | 서수 → `last_list.items[0]` | narrative RAG(retrieve→generate) | 설명 + [근거 N] | `subject=items[0](source=list)` |
| 7 | 색상은 무시하면 얼마나 부족해? | 모드 후속 → 직전 대상(6의 세트)·추천 문맥 | `analyze(subject, ignore_color)` (+필요 시 recommend 재계산) | "색상 무시 기준으로 N개 부족(정확 일치 기준 M개)" + 부족 표(접힘) | `mode=ignore_color` |

- 7단계는 **현재 대상이 있으면 그 세트 분석**, 대상이 없고 직전 목록이 추천이면 **같은 추천 파라미터로 재계산**한다.
- 2단계에서 결과가 0건이면 "그중 2021년 출시는 없습니다. 목록의 출시 연도: …"로 답하고 상태를 바꾸지 않는다.

## 3. 대화 상태·저장 구조·API

### 3.1 저장 구조 (`data/user.sqlite`, 비파괴 추가)
| 테이블 / 열 | 용도 |
|---|---|
| `schema_meta(key PK, value)` | 스키마 버전(`user_schema_version`). 마이그레이션 실행기가 관리한다 |
| `conversations(id TEXT PK, uid, title, created_at, updated_at, legacy_thread NULL)` | **통합 대화 ID**. `legacy_thread`는 이관 출처 |
| `conversation_state(conversation_id PK, state_json, version INT, updated_at)` | 구조화 상태(§3.2). **낙관적 버전** |
| `conversation_turns` + `conversation_id`, `request_id UNIQUE`, `kind`, `state_version` | 기존 테이블에 열만 추가한다(`ALTER TABLE ADD COLUMN`) |
| `turn_subjects(turn_id, set_num, role)` | 턴과 세트의 연결. role = `primary`·`compared`·`listed`. F2009 세트별 조회용 |
| `chat_requests(uid, request_id, conversation_id, status, turn_id, created_at, PK(uid, request_id))` | 요청 멱등 장부(`running`·`done`·`failed`) |
| `collections` + `version INT DEFAULT 0` | 컬렉션 낙관적 버전 |
| `collection_events(id, collection_id, request_id UNIQUE NULL, set_num, op, qty_before, qty_after, created_at)` | 컬렉션 변경 기록 + 변경 멱등 |

- 기존 `thread` 열은 유지한다. 새 턴은 `thread`에 대표 대상 세트 번호 또는 `general`을 넣는다(구 API 읽기 호환).

### 3.2 상태 모델 (`services/dialogue_state.py`)
```text
DialogueState
  subject   : {set_num, source: explicit|list|card|ui, turn_id} | null   ← 현재 대상
  last_list : {kind: search|recommend|candidates, turn_id,               ← 사용자가 실제로 본 목록
               items: [set_num …표시 순서],
               spec: FilterSpec(dict) | null,                            ← 검색 조건 (정제용)
               rec:  {mode, top_n, scope} | null}                        ← 추천 파라미터 (재계산용)
  compare   : [set_num …]                                                ← 명시적 비교 대상
  mode      : exact | ignore_color                                       ← 부품 분석 모드
  pending   : {kind: target|quantity|confirm, options: [set_num …],      ← 해결 안 된 되묻기
               request: {intent, op?, qty?, question, mode?}} | null     ← 이어서 처리할 요청
```
- **"첫 번째" 기준**: `last_list.items`, 즉 **화면에 표시한 순서**다. 재검색 순서가 아니다.
- 응답 `AnswerOut.items: [{rank, set_num, name, year, num_parts, missing?, lots_missing?}]`를 추가한다. 화면 카드와 `last_list`가 **같은 원천**을 쓴다.
- 상태는 턴 저장과 **같은 트랜잭션**에서 갱신한다. `version`이 다르면 충돌(409)로 처리한다.

### 3.3 해석 우선순위 (`services/context_resolver.py`, 결정적, 라우터 이전)
1. **pending 응답**: pending이 있고 입력이 선택지와 맞으면(번호·서수·이름·"응/아니") 저장된 원래 요청을 이어서 실행한다. 맞지 않으면 pending을 버리고 새 질문으로 처리한다.
2. **명시 대상**: 질문 속 세트 번호·고유 별칭 → 새 대상.
   - "그중"과 함께 와서 목록 밖이면 명시 대상을 우선하고 "목록 밖 세트입니다"라고 경고한다.
   - 세트 2개 이상 + 비교 단서면 `compare`에 둔다.
3. **서수**(첫/두/세 번째, N번, 마지막, 1위) → `last_list.items[i]`. 목록이 없거나 범위를 벗어나면 되묻는다.
4. **"그중/그 중에서/이 중/여기서"** → 목록 정제.
   - search: `spec ∧ 새 조건 ∧ set_num ∈ items`
   - recommend: 같은 추천 결과에 조건 필터(연도·부품 수·부족 수)
   - 정제 결과는 새 `last_list`가 된다(표시 순서는 원래 순서를 보존한다).
5. **지시어**(그거/이거/그 세트/그 기체/얘): 현재 대상 → 없으면 `last_list`가 1건일 때 그 항목 → 여러 건이면 후보 카드로 되묻는다(**추측 금지**).
6. **모드 후속**: 정규식 `색(상|깔)\S*\s*(무시|상관\s*없)` 또는 `ignore_color_cues` → `mode=ignore_color`, 직전 분석·추천 문맥으로 재계산한다.
7. 대상이 필요 없는 의도(새 조건 검색, "내 부품으로 뭐 만들어")는 대상을 쓰지 않고, 지우지도 않는다.

**충돌 시 우선순위**: 명시 대상 > pending 선택 > 서수(목록) > 지시어(현재 대상) > UI 선택. 모호하면 되묻는다.

**초기화 규칙**
| 사건 | subject | last_list | compare | mode | pending |
|---|---|---|---|---|---|
| 새 대화 | 비움 | 비움 | 비움 | exact | 비움 |
| 대상 변경(명시·카드·서수) | 새 값 | 유지 | 비움 | 유지 | 비움 |
| 대상 해제(UI) | 비움 | 유지 | 비움 | 유지 | 비움 |
| 새 검색·추천 | 유지 | **교체** | 유지 | 추천이면 rec.mode | 비움 |
| 되묻기 발생 | 유지 | 후보면 교체 | 유지 | 유지 | 설정 |

**라우터 연결**
- 해석기가 정한 대상을 기존 `selected_set` 인자로 넘긴다. `answer(..., context=ResolvedContext)`로 정제 spec·allow·mode·compare를 전달한다.
- router-v4 메시지에 `context: {subject, last_list_kind, last_list_size, pending_kind, mode}`를 넣는다. `_cached` 키는 메시지 전체 해시이므로 **문맥이 다르면 캐시가 분리된다**.
- 보유 수량은 매 턴 컬렉션 DB에서 읽는다. 캐시 키에는 `collection.version`을 넣는다(추천 계산 결과를 캐시할 때).
- T-019 `_rules`(미지원 속성·fact 속성 단서·두 세트 비교)는 유지한다.

### 3.4 API (FastAPI, 구 API 호환)
| 메서드·경로 | 용도 |
|---|---|
| `POST /api/conversations` | 새 대화 → `{id}` |
| `GET /api/conversations` | 대화 목록(제목·갱신 시각·대상) |
| `GET /api/conversations/{id}` | 턴 + 상태 요약 → **새로고침 복원** |
| `PATCH /api/conversations/{id}/subject` | `{set_num \| null, version}` 대상 변경·해제 |
| `DELETE /api/conversations/{id}` | 대화 삭제(턴·상태) |
| `GET /api/sets/{set_num}/history` | **세트별 기록**(F2009) |
| `POST /api/chat` | `{conversation_id, question, request_id}` → SSE `stage* → result{turn, state, action?}` |
| `GET/PUT /api/collection` | `version` 추가. 낡은 PUT은 409 |
| `GET /api/threads*` | **읽기 전용 호환**(제출까지). 이관된 레거시 대화를 보여 준다 |
- 처리 중 잠금 키는 `(uid, conversation_id)`다.

## 4. 대화 기반 컬렉션 변경

### 4.1 표현의 의미
| 표현 | 의도 | 처리 | 답변 예 |
|---|---|---|---|
| "75301 하나 등록해줘" | 설정 qty=1 | 바로 반영 | "75301-1 … 보유 0개 → 1개로 등록했어요" |
| "그거 하나 더 추가해줘" | 증가 +1 | 대상이 명확하면 반영(멱등 키 필수) | "… 1개 → 2개" |
| "실제로는 두 개야" | 현재 대상 qty=2로 수정 | 반영 | "… 1개 → 2개로 고쳤어요" |
| "그거 보유 목록에서 빼줘" | 제거 | 반영 | "… 2개 → 목록에서 뺐어요" |
| "그거 가지고 싶어 / 사고 싶어" | 변경 없음 | 저장하지 않음 | "보유 목록은 그대로예요. 등록하려면 '등록해줘'라고 말해 주세요" |
| "그거 하나 있어" | 보유 진술 → qty=1 | 미보유면 반영하고 그 사실을 알림. **이미 더 많이 보유하면 확인**(pending confirm) | "75301-1을 1개 보유로 기록했어요" |
- 의도는 결정적 패턴 사전 `config/collection_intents.yaml`(동사·수량 표현·부정어)로 판정한다. 동사·수량·대상이 모두 명확할 때만 바로 실행한다.
  - 수량을 못 읽으면 되묻고(`pending.kind=quantity`), 대상이 모호하면 후보로 되묻는다.
- 검증
  - 세트 존재: `planner.sets.get_set`
  - 수량: 정수, 1 이상 `collection.max_qty`(settings, 기본 99) 이하
  - 범위 밖이어도 DB에 있으면 허용한다(PRD B-01).

### 4.2 실패·재시도·동시성
- **원자성**: 한 SQLite 트랜잭션(`BEGIN IMMEDIATE`)에서 순서대로 처리한다.
  1. `collection_events`에서 `request_id`를 조회한다. 있으면 **저장된 결과를 그대로 반환**한다.
  2. 현재 수량을 읽고 새 수량을 계산한다.
  3. `collection_sets`에 반영한다(0이 되면 행 삭제).
  4. `collection_events`를 기록하고 `collections.version += 1`.
  5. 커밋한다.
- **성공 알림은 커밋 후에만** 한다. 실패하면 롤백하고 "보유 목록을 바꾸지 못했어요(변경 없음)"라고 안내한다.
- **동시 수정**: 다른 대화·편집기의 변경은 트랜잭션 직렬화로 손실 갱신이 없다. 편집기 PUT은 `version`이 다르면 409를 내고 다시 불러오게 한다.
- **요청 ID**: 웹은 제출마다 `crypto.randomUUID()`, Streamlit은 입력 제출 시 세션 값으로 발급한다.
  - `chat_requests`가 `running`이면 409 busy를 낸다.
  - `done`이면 저장된 턴을 다시 보낸다(SSE 재연결·중복 제출·재시도).
- **단계 분리**: "등록하고 뭐 만들 수 있는지도 알려줘"는 ① 변경(커밋) → ② 추천·설명으로 나눈다. ②가 실패해도 ①은 다시 실행하지 않고, 답변에 "등록은 완료, 추천은 실패"를 표시한다.

## 5. F2009 충족 방식과 마이그레이션

### 5.1 원문 요구
- F2009(요구사항정의서 p.14): "사용자는 목록에서 질문할 항목을 선택할 수 있어야 한다", "선택한 항목별로 대화 기록이 구분되어 유지되어야 한다".
- 4.4 확인 항목(p.18): "항목을 바꿨을 때 이전 대화가 섞이지 않는지 확인한다".
- F2011(p.15): "제시된 항목을 선택하면 해당 항목에 대한 질문을 이어갈 수 있어야 한다".

### 5.2 세 가지 관점 분리
| 관점 | 정의 | 사용처 |
|---|---|---|
| ① 통합 타임라인 | 한 `conversation_id`의 모든 턴(시간순) | 대화창 |
| ② 세트별 기록 | `turn_subjects.role ∈ {primary, compared}`인 턴(모든 대화 통합) | 보조 패널 "세트별 기록", `GET /api/sets/{n}/history` |
| ③ 모델 문맥 | 현재 대화에서 **현재 대상이 primary인 턴만** P3 history로 쓴다. 라우터에는 직전 1턴 + 구조화 상태만 준다 | `chat_turn` → `orchestrator.answer(history=…)` |

### 5.3 검증 기준 (세트 태그만으로 충족했다고 보지 않는다)
- (a) A 세트 기록에 B가 primary인 턴이 0건이다. compared 턴은 "비교: A·B" 배지와 함께만 나타난다.
- (b) 같은 대화에서 대상을 A → B로 바꾼 뒤, B 질문의 **P3 history에 A 턴이 없다**(대역 `ask`가 받은 history 검사).
- (c) 세트별 기록이 API·웹·Streamlit 모두에서 보인다. 대상을 바꾸면 패널 내용이 그 세트 기록으로 바뀐다(4.4 캡처).
- (d) 비교 질문("75192랑 75375 차이")은 두 세트에 compared로 연결되고, 양쪽 기록에 나타난다.
- (e) 검색 결과에 **나열만 된** 세트(listed)는 세트별 기록에 나타나지 않는다.
- (f) 카드에서 세트를 고르면 같은 대화에서 그 세트에 대한 질문이 이어진다(F2011).

### 5.4 비파괴 마이그레이션
1. 실행 전에 `data/user.sqlite`를 `data/backup/user-<timestamp>.sqlite`로 복사한다.
2. 새 테이블과 열을 추가한다(`CREATE TABLE IF NOT EXISTS`, 열 존재 확인 후 `ALTER TABLE ADD COLUMN`).
3. 기존 `(uid, thread)`마다 레거시 대화 1개를 만든다(`legacy_thread`).
   - 제목: 세트 thread는 "75192-1 Millennium Falcon", `explore`는 "탐색(이전)", `collection`은 "내 컬렉션(이전)"
4. 기존 턴에 `conversation_id`를 채운다. 세트 thread 턴은 `turn_subjects(primary)`로 연결한다. explore·collection 턴은 대상 없음이다.
5. 상태는 비워 둔다. 세트 thread 대화는 `subject=그 세트(source=ui)`로 시작한다.
6. 원 행은 지우지 않는다. **두 번 실행해도 결과가 같다**(멱등). `schema_meta`에 버전을 기록한다.
- **구 API·화면 전환**
  - 새 웹은 새 엔드포인트만 쓴다. 구 `/api/threads*`는 읽기 전용으로 남긴다.
  - Streamlit은 같은 서비스 함수로 동시에 전환한다.
  - 기존 thread 키 의존 테스트는 **같은 의미(F2009 분리)를 새 계약으로 검증하도록 바꾼다**(삭제 금지).
- **새로고침 복원**
  - 웹: localStorage에 `{uid, conversationId}`를 두고 `GET /api/conversations/{id}`로 턴·상태를 다시 그린다.
  - Streamlit: `?uid=&conv=`를 쓴다.

## 7. 평가 일정과의 관계·미결 사항
- **일정**: T-020(완료) → **T-021~T-026 대화 UX** → M7 제출. 제출용 화면 캡처는 T-025 이후 최종 화면으로 찍는다.
- **되돌리지 않는 것**: ADR-017 검색 기본값(MMR·질문 원문), T-019 라우팅 규칙, 수치 사후 검증, 인용 필터, 2노드 그래프.
- **회귀 기준(T-026)**
  - 라우팅: 40문항 ≥ 39, holdout 12/12·8/8
  - 검색: 35/40
  - RAG 전후: 8문항 점수 유지
  - planner: 고정 테스트 계산값 동일
  - 신규 다턴 시나리오: 7단계 + 변형 통과
- **사용자 결정이 필요한 미결 사항** (문서에는 권장안을 기본값으로 둔다)
  1. 보유 진술이 기존 수량보다 적을 때("하나 있어", 현재 2) → 권장: **줄이기 전에 확인**
  2. 레거시 대화 이관 단위 → 권장: **기존 thread마다 대화 1개**(합치지 않음)
  3. 여러 대화(대화 목록·새 대화) 제공 → 권장: **제공**
  4. 구 API 호환 기간 → 권장: **제출까지 읽기 전용 유지**
