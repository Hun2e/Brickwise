## 3. 핵심 데이터 규칙 (검증 완료)

### 3.1 부품 집계 규칙 [확인]
- **세트의 공식 부품 수(`sets.num_parts`) = 스페어를 뺀 인벤토리 부품 합 + (미니피그 수량 × 미니피그 부품 수)**
- 범위 332세트 중 **331세트가 정확히 일치**했습니다 (스페어 포함 등 다른 정의는 24~68세트만 일치).
- 따라서 Build Planner의 보유·필요 부품은 이 정의로 계산하고, **`num_parts` 재현을 데이터 무결성 테스트로 씁니다.**
- 미니피그는 `inventory_minifigs.fig_num` → `inventories(set_num = fig_num)` → `inventory_parts`로 전개합니다 (707/707 인벤토리 존재 [확인]).

### 3.2 식별자 표준화
| 대상 | 표준 키 | 규칙 |
|---|---|---|
| 세트 | `set_num` (예: `75192-1`) | 사용자 입력 `75192` → `-1` 우선, 여러 개면 후보 제시 |
| 부품 | `(part_num, color_id)` | 대소문자 유지, 공백 제거. `color_id = -1`(Unknown)은 exact 매칭 불가 |
| 미니피그 | `fig_num` (예: `fig-000123`) | 부품 전개 후에는 부품 키로만 집계 |
| 문서 | `doc_id` = `bp:{page_id}` / `wp-en:{page_id}` / `wp-ko:{page_id}` | 출처 접두어로 충돌 방지 |
| 청크 | `entity:{doc_id}:{seq}` (기체·캐릭터 문서, 메타 `sets` 배열로 세트 연결), `series:{doc_id}:{seq}` (시리즈 문서), `{set_num}:{doc_id}:{seq}` (세트 전용 문서, Brickipedia 승인 시) | 기체 문서는 1벌만 저장하고 `sets`는 합집합으로 갱신 → 덮어쓰기 없음 (ADR-008) |
| 인벤토리 판본 | 세트별 최대 `version` | 판본 번호는 근거 카드에 표시 |

### 3.3 부품 대체 규칙 (L5)
| 관계 | 의미 [추정: Rebrickable 정의 기반] | 대체 허용 |
|---|---|---|
| M | 몰드 변형 | `mold_variant` 모드에서 허용 |
| A | 대체 부품 | `mold_variant` 모드에서 허용 |
| P | 인쇄 버전 | **불허** (외형이 다름) |
| R, B, T | 짝·하위 부품·패턴 등 | 불허 |
→ 관계 유형의 정확한 의미는 데이터 PoC에서 Rebrickable 도움말로 다시 확인합니다.

## 4. 저장 구조

### 4.1 SQLite (`data/lego.sqlite`, git 제외, 스크립트로 재생성)
```sql
-- 원본 적재 (CSV 컬럼 그대로) [컬럼 확인]
themes(id PK, name, parent_id)
colors(id PK, name, rgb, is_trans, num_parts, num_sets, y1, y2)
part_categories(id PK, name)
parts(part_num PK, name, part_cat_id, part_material)
part_relationships(rel_type, child_part_num, parent_part_num)
elements(element_id PK, part_num, color_id, design_id)
sets(set_num PK, name, year, theme_id, num_parts, img_url)
minifigs(fig_num PK, name, num_parts, img_url)
inventories(id PK, version, set_num)
inventory_parts(inventory_id, part_num, color_id, quantity, is_spare, img_url)
inventory_sets(inventory_id, set_num, quantity)
inventory_minifigs(inventory_id, fig_num, quantity)

-- 파생 (적재 후 생성)
set_scope(set_num PK, scope)            -- 'core' | 'compare_only'
set_root_theme(set_num PK, root_theme_id, root_theme_name, subtheme_name)
set_parts_flat(set_num, part_num, color_id, quantity,  -- 스페어 제외 + 미니피그 전개, 최신 판본
               PRIMARY KEY(set_num, part_num, color_id))
ko_aliases(alias PK, canonical_en, kind, source, verified)  -- kind: vehicle/character/set/theme

-- 사용자 (★ 별도 파일 data/user.sqlite — lego.sqlite는 적재 때마다 통째로 교체되므로 분리. T-002에서 결정)
collections(id PK, created_at)
collection_sets(collection_id, set_num, qty, PRIMARY KEY(collection_id, set_num))
collection_adjustments(collection_id, part_num, color_id, delta)

-- 수집 이력 (NF2002)
fetch_log(source, query, doc_id, revid, fetched_at, status, PRIMARY KEY(source, query, doc_id))
```
- 인덱스: `inventory_parts(inventory_id)`, `set_parts_flat(part_num, color_id)`, `sets(year)`, `sets(theme_id)`
- 157만 행 적재는 SQLite로 처리할 수 있다고 봅니다 [추정]. PoC에서 적재 시간과 DB 크기를 측정합니다.

## 5. 수집 파이프라인

```
① Rebrickable CSV 다운로드 (하루 1회 이하, ETag/크기 비교로 변경 시에만)
   → ② SQLite 적재 → ③ 파생 테이블 생성 → ④ 무결성 검사(§6)
   → ⑤ 범위 선정(set_scope) → ⑥ 항목 텍스트 → set_meta 색인
⑦ 질문 시점(또는 사전 수집 스크립트):
   프롬프트1 검색어 추출 → Brickipedia/위키 검색 → 프롬프트2 선별 → 본문 수집 → 정제 → 청킹 → set_docs 색인
```

### 5.1 Brickipedia 수집 (L2 승인 후)
- **세트 자체 문서 찾기**: `action=opensearch&search={번호}&namespace=0` 결과에서 제목이 `"{번호} "`로 시작하는 문서를 고릅니다 (표본 40/40 일치 [확인]). 실패하면 `list=search`로 대체합니다.
- **본문**: `action=parse&page={title}&prop=text|revid|sections`
  - HTML을 표준 라이브러리 `html.parser`로 텍스트로 바꿉니다.
  - 인포박스·내비박스·갤러리·각주 블록은 버리고, 섹션 제목은 남깁니다.
  - 정제 규칙은 PoC에서 확정합니다.
- **변경 감지**: `revid`를 `fetch_log`에 저장하고, 다시 수집할 때 revid가 같으면 건너뜁니다.
- **예절**: User-Agent `BrickArchivePlanner/0.1 ({WIKI_CONTACT}) python-requests`, 요청 간격은 settings 값, 429·5xx는 `Retry-After`를 따르는 재시도.

### 5.2 위키백과 수집
- 시리즈 문서 시드: `Lego Star Wars`(영, 98KB), `레고 스타워즈`(한, 10.7KB) [확인]
- 기체·작품 문서는 프롬프트1이 검색어를 뽑으면 `list=search`로 찾습니다.
- 본문은 `prop=extracts&explaintext=1`(TextExtracts)을 기본으로 씁니다 [추정: 위키백과에서 제공. PoC로 확인].
- 시리즈 문서는 `item_id=series`로 색인해 모든 세트 질문에서 검색할 수 있게 합니다.

### 5.3 한국어 별칭 사전 (D-05)
1. 범위 세트명에서 기체·캐릭터 명사를 추출합니다 (규칙 + 빈도). 예: "Millennium Falcon", "X-wing Starfighter"
2. 영어 위키 문서를 찾고 `prop=langlinks&lllang=ko`로 한국어 제목 후보를 얻습니다.
3. 후보 없는 항목은 LLM 음역 후보를 `verified=0`으로 넣습니다. **검수 전에는 화면의 공식 명칭으로 쓰지 않고 검색 확장에만 씁니다.**
4. 사람(PM)이 검수해 `verified=1`로 바꿉니다.

### 5.4 LEGO 링크 생성 (콘텐츠 비수집)
- 설명서 페이지 URL 패턴(예: `https://www.lego.com/service/building-instructions/{번호}`)만 생성합니다 [추정: 패턴은 PoC에서 확인].
- 링크가 존재하는지 HEAD로 확인할지는 약관 해석상 보수적으로 **하지 않고**, 배지를 "링크(미확인)"로 둡니다.

## 8. 비용·토큰 추정 [추정]
- 세트 문서: 332건 × 정제 후 약 2~4KB → 약 1MB → 임베딩 약 25만~35만 토큰
- 시리즈 문서: 100~200KB → 약 5만 토큰
- 메타 텍스트: 약 600건 × 100토큰 = 6만 토큰
- → 초기 색인 전체 **50만 토큰 미만** 예상. 임베딩 캐시로 재색인 비용은 변경분만 발생합니다. 실제 값은 PoC에서 `usage_metadata`로 측정합니다.
